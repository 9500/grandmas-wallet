Grandma's Wallet

A Bitcoin Cash wallet whose keys can be replaced by a trusted recoverer after a public waiting period. Every coin has its own address and key, as in an ordinary HD wallet. A single controller on chain can release any of them to a new owner. Applications give authority to a token in the wallet, so recovering an application position is the same as moving a coin.

The design

Every address of the wallet can be spent in two ways. Its own key spends it directly, like any single-key address. The wallet's controller can also release it, and the controller obeys whoever owns the wallet's identity today. Recovery changes the owner of the identity. The new owner then moves every coin and token to addresses of its own keys.

Two ways into every coin

The parts

Wallet

Controller. One coin holding the identity NFT. Its state names the owner's controller key, the recoverer's key and the waiting period. It moves only for recovery, sweeps and the vault.

Wallet

Recoverable addresses. One per coin, each with its own key for every day and a hidden link to the identity for recovery. A second kind, the vault address, has no key and never changes.

Recovery

Recoverer and viewing key. The recoverer can replace the owner after the waiting period. It also keeps the viewing key, which lets a new device find every address. Neither lets it spend.

Applications

Three rules and a connection. Authority is a token. The wallet's inputs and outputs are the wallet's business. The template says what a token means. The wallet builds each transaction from the application's XO template.

Identity and controller

The wallet's identity is the token category of one NFT. The coin that holds this NFT is the controller. The NFT's commitment is the controller's state, 69 bytes. The controller's script accepts four actions and always sends the NFT back to itself with the next state.

ActionSigned byWhat it doesUsed for
ownerAuthorizeOwner's controller keyContinues the controller unchanged as Active. Cancels a pending request.Sweeps, spending from the vault, cancelling a request
requestRecoveryRecoverer's keyMarks the state Pending and names the proposed new owner key. The waiting period starts.The first step of recovery
finalizeRecoveryRecoverer's keyOnly after the waiting period. Installs exactly the proposed key and raises the epoch by one.The second step of recovery
ownerUpdateOwner's controller keyReplaces the owner key, the recoverer or the waiting period.Moving to a new seed without the recoverer; changing the recoverer

Rules that hold for every action: the controller is input 0 and output 0 of its transaction, the NFT and the coin's value continue, and the signature must cover every input and output.

The controller's script does not check its own first state. Before trusting an identity, a wallet checks the transaction that created it (one NFT of the category, no way to make another, a valid first state, locked by the controller script) and follows every step of the controller from there to today.

Two properties carry the scheme

  • The waiting period is enforced by the network. It is a relative time lock on the controller's own coin. Nobody can shorten it.
  • The recoverer never gains spending power. A coin released through the controller requires the controller to continue unchanged, with the same owner and no request pending. A request leaves a claim pending and a completion changes the owner, so neither can carry coins with it. This check is one shared function, ownerApproves(identity), used by every address script.
function ownerApproves(bytes32 identity) {
    // Input 0 is this identity's controller.
    require(tx.inputs[0].tokenCategory == identity + 0x01);
    bytes state = tx.inputs[0].nftCommitment;
    require(state.length == 69);
    require(state.split(1)[0] == 0x01);
    // It continues as Active with the same owner, epoch, recoverer and delay.
    require(tx.outputs[0].tokenCategory == identity + 0x01);
    require(tx.outputs[0].nftCommitment == 0x0100 + state.slice(2, 49) + bytes20(0));
}

Only the owner-signed ownerAuthorize can produce that successor. The owner's signature on the controller, which covers the whole transaction, is therefore what approves the release. The simulator under A wallet's life shows the state byte by byte.

Keys and addresses

The wallet works like an HD wallet and uses the same building blocks: twelve words (BIP39) and a tree of keys computed from them (BIP32). One seed on the phone gives a key for every address, and every coin can sit at its own address. What is added is a second, hidden way into each address, and a viewing key that lets someone other than the phone find the addresses again.

Seedon the phone only
Twelve words, made on the phone. Every key below is computed from them, and nothing random is added later. The user is not asked to write them down. Losing the phone loses the seed.
Controller keyfrom the seed
One key on a branch of its own. Its hash is the owner entry in the controller. It is used for nothing else and appears in no address.
Address keysfrom the seed
One branch whose children are the address keys, counted from 0. There are two kinds: given out, for addresses the user hands to people who pay them, and change, for change and for coins and tokens that an application's transaction sends to the wallet.
Blinding seedfrom the seed
32 bytes on a third branch. It gives every address a secret: secret = hash256(blinding seed ‖ kind ‖ number).
Viewing keyon the phone and with the recoverer
Two values: the extended public key of the address branch, which gives every address's public key and no private key, and the blinding seed. Together with the identity they find every coin. They cannot spend one. Either value alone finds nothing.
Identitypublic, on chain
The token category of the controller's NFT. It is not written in any address, and it cannot be worked out from the seed: it exists only once the controller has been created.
ValueProposed place in the key tree
Controller keym / P' / S' / 0' / 0
Address key, kind c, number im / P' / S' / 1' / c / i   (c = 0 given out, 1 change)
Blinding seedSHA-256 of the private key at m / P' / S' / 2'
Funding keym / P' / S' / 3' / 0

P is XO's purpose number, 2415 on mainnet and 42415 on test networks. S is a constant for this scheme that is still to be fixed. Whether the XO engine can be made to use exactly these keys is one of the first trials in the plan; if it cannot, the wallet's own code handles its coins beside the engine.

Finding everything again

A device that holds the identity and the viewing key restores the wallet the way any HD wallet is restored. For each kind of address it derives number 0, 1, 2 and so on, looks each up on chain, and stops after a run of unused ones: 20 for addresses given out, 5 for change and for vault addresses. For each address it finds it also has the secret, which is what the recovery path needs. No list of addresses has to be kept anywhere.

After a recovery the new device has a new seed and a new viewing key. It gives the new viewing key to the recoverer before the waiting period starts, so the wallet is never without a recovery path. Earlier viewing keys are kept: they find payments that still arrive at earlier addresses.

The first coins

An address needs the identity, and the identity is the identifier of a transaction, so the wallet's very first coins cannot arrive at a recoverable address.

  1. Fund. The user sends coins to the wallet's funding address, an ordinary single-key address of the funding key.
  2. Prepare. The wallet pays itself, so that it has a coin that is output 0 of its transaction. That transaction's identifier is the identity.
  3. Create and move. A transaction spends that coin and creates the controller. The rest goes to recoverable addresses, and a small amount is set aside for the recoverer's fees.

The funding address is not recoverable. It is shown only until the wallet exists. The wallet gives out no address until the transaction that defines the identity is confirmed. The first coins can be traced to the creation of the identity; coins received later cannot.

How an address is made

The wallet makes a new address whenever one is needed. Making one writes nothing on chain and does not involve the controller.

WhenKind of addressWhich number

The user wants an address to publish, or to be paid at for yearsVaultThe next one

Every address is built in the same steps. Choose a kind and a number to follow them for one example wallet.

number 0

  • The phone can do every step. A holder of the viewing key can do all but the private key: it gets each public key from the extended public key.
  • Nobody can go backwards from an address. The address is a hash of the script. The tag inside the script is a hash of the identity and a secret that only the viewing key gives.
  • Two addresses of one wallet share nothing visible. Each has its own key and its own secret, so each has its own tag.
  • The payer sees an ordinary script address. Nothing shows that it is recoverable or which wallet it belongs to.
  • The wallet never shows an address more than 20 numbers past the last one that was used. A later scan stops after 20 unused addresses, so this keeps every address it gave out findable.

The recoverable address

A script address (P2SH32) with two ways to spend.

contract RecoverableAddress(bytes32 tag, bytes20 keyHash) {
    // Everyday path: the key this address was made for.
    function spend(pubkey pk, sig s) {
        require(hash160(pk) == keyHash);
        require(checkSig(s, pk));
    }
    // Recovery path: whoever owns the identity today, through the controller.
    function sweep(bytes32 identity, bytes32 addressSecret) {
        ownerApproves(identity);
        require(hash256(identity + addressSecret) == tag);
    }
}

contract VaultAddress(bytes32 tag) {
    // No key. Only the identity's current owner, through the controller.
    function spend(bytes32 identity, bytes32 addressSecret) {
        ownerApproves(identity);
        require(hash256(identity + addressSecret) == tag);
    }
}

A trial compilation gives 96 bytes of rules for the recoverable address and 75 for the vault address, before the tag and the key hash are added. From the script size, spending such a coin by its key takes about twice the bytes of an ordinary single-key input. Neither script has been tested yet.

Recoverable address

The wallet's ordinary address, a fresh one for each coin, token and change output. Used for everything the wallet does with applications. After a recovery its contents are swept to addresses of the new seed.

Vault address

For an address that must outlive a key change: one published to be paid at any time, or a payout address agreed long before the payout arrives. It is meant to be used more than once. Spending from it needs the controller at input 0, so a coin is moved from the vault to an ordinary address before an application can use it.

    A wallet's life

    Press the actions in any order. The strip shows the controller's 69 bytes; press a field to read what it is for. The cards show where the coins and tokens sit. Each one is at its own address; the cards group them by the seed their addresses were made from.

    Controller and addresses

      Things to try: complete a recovery and use the loan before sweeping. Complete a recovery and let the earlier seed act before the sweep. Request a recovery, then pay someone, and see that the request stays pending.

      Recovery flow

      1. 0

        Setup, while all is well

        Owner and recoverer

        The wallet creates its controller, naming the recoverer's key and the waiting period. It sends the recoverer a recovery kit, signed by the owner and sealed so that only the recoverer can open it. The recoverer checks the kit against the chain and leaves a signed confirmation. Only then does the wallet say that recovery is on.

      2. 1

        A new device asks

        New device and recoverer

        The new device makes a new seed. It gives the recoverer the hash of its controller key, its own viewing key and a key for the answer. The recoverer satisfies itself that the person is the wallet's user; how it does so is its own process, and the design depends on it.

      3. 2

        Request

        Recoverer

        The recoverer signs requestRecovery naming that key. The controller is now Pending, on chain, and the waiting period has started.

      4. 3

        Wait, and the owner's chance to refuse

        Owner, if the phone is not lost

        The wallet watches its controller on several servers. If a request appears that the owner did not ask for, the owner cancels it with one signature of the controller key. Ordinary payments do not touch the controller, so they do not cancel a request. The cancel is a transaction of its own, by hand or automatic, and the wallet keeps a small coin to pay for it.

      5. 4

        Complete and hand over

        Recoverer

        After the waiting period the recoverer signs finalizeRecovery. The proposed key becomes the owner and the epoch goes up. No coin has moved. The recoverer now gives the new device the identity and every earlier viewing key, sealed to the device.

      6. 5

        Sweep

        New device

        With the identity and the earlier viewing keys the new device finds every address in use. It moves what is there to addresses of its own seed, in transactions that carry the controller, signed with ownerAuthorize. Each swept input shows the identity and its address secret. Coins, fungible tokens and NFTs move the same way. The fee comes out of the swept coins. A large wallet is swept in several transactions, the most valuable coins first.

      7. 6

        Understand what the tokens are

        New device, with the applications' templates

        A swept NFT is already under the new owner's control. To show it as "a jar with 0.3 BCH that opens in March" the wallet needs the application's template, from its backup or from the application when the user connects again. Recovery does not wait for this.

      8. 7

        Keep watching

        New device

        The new device watches the controller, and it keeps watching the earlier addresses for payments that still arrive there. See A payment to an old address.

      The recovery kit and the recoverer's key

      • The kit contains the identity and the transaction that created it, the recoverer's key for this wallet, the viewing key, where the sealed backup is kept and how to read it, and the settings as the owner saw them, for the recoverer to compare with the chain. It fits in one link or one QR code.
      • The recoverer's key is one per wallet, not one per coin. Only its hash is on chain, in the controller. No address contains it, and the recoverer never signs for a coin. It signs two kinds of transaction: the request and the completion.
      • The recoverer uses a different key for every wallet, so two wallets with the same recoverer show nothing in common. By default the owner's phone makes this key as a separate set of twelve words, puts its hash into the controller, seals the words into the kit and does not keep them.
      • The recoverer's fees are set aside when the wallet is created: enough for three requests and one completion.

      What each party holds and can do

      PartyHoldsCan doCannot do
      Owner's deviceThe seed; the identity; the viewing keySpend, cancel a request, change the recoverer
      RecovererIts key for this wallet; the identity; the viewing keyRequest and complete a recovery. See every address and balance of the wallet.Spend anything. Shorten the wait. Complete with a key other than the one requested.
      New deviceIts own new seed. After completion: the identity and the earlier viewing keys.After completion: sweep and spendAnything before the wait is over
      Backup storesSealed records: copies of the viewing keys, trusted templates, notes on which template made which token, labelsHand the records backRead them

      What the waiting period does and does not protect. It protects against a recoverer who acts without being asked, as long as the owner notices in time. A recoverer who names their own key and is not cancelled gets the wallet. It does not protect against a thief who can use the owner's phone: such a thief can spend at once, as with any wallet.

      If a recovery completes against the owner's will, the owner's keys still spend every coin that has not been swept. A wallet that finds itself owned by a key it does not hold offers to move its coins out at once, to a wallet with a new identity. Coins at vault addresses cannot be saved this way.

      A payment to an old address

      After a recovery, someone may still pay an address the wallet gave out before: an old invoice, an address saved in an exchange's withdrawal list. That coin is not lost. The new owner collects it through the controller, by the same path as the sweep. This is not the vault address; the two are compared below.

      1. The coin lands at the old address. Receiving runs no script, and nothing on chain tells the payer that the wallet has a new owner.
      2. The new device notices it. It holds the earlier viewing key, which the recoverer handed over. From it the device derives the same addresses the old phone used and keeps watching them, including the 20 numbers past the last one used.
      3. The new device collects it. One transaction: the controller at input 0, approved by the new owner, and the coin, unlocked by showing the identity and that address's secret. The secret comes from the earlier viewing key. The coin goes to an address of the new seed.
      4. Until then the coin has two masters. The key the address was made for is on the lost phone, and it still opens the address. This matters only if someone can use that phone.

        So the wallet shows a fresh ordinary address for a one-off payment and offers a vault address for anything that is published or stored by others. After a recovery it tells the user that people who pay them need a new address.

        What others can see

        Addresses are not linked to each other or to the identity until the wallet is recovered. Choose who is looking.

        The same six addresses, seen by

        EventWhat becomes linked, in public

        A cancel or a change of settingsThe coin that pays the fee, and its change. The wallet keeps a small coin apart for this.

        Everything else the wallet does leaves no link to the identity.

        The controller is readable on purpose

        Anyone can see that a controller exists, and read its state. It is not linked to any address until a sweep. Hiding the state behind a hash would gain little: every transaction of the controller has to show the state to the script, so it would become public the first time the controller is used. Two simple measures do more:

        • The recoverer uses a different key for every wallet. Two wallets with the same recoverer then show nothing in common.
        • The owner's controller key is used for nothing else. It never appears in an address.

        What a recovery reveals

        A sweep has the controller as its first input and shows the identity in every swept input. Everything the wallet held at that moment is tied together, in public. Coins received afterwards at new addresses are unlinked again. Limiting this would take several controllers, each covering part of the addresses. Hiding it fully would take a zero-knowledge proof checked in script, which Bitcoin Cash cannot practically do today as far as we know. Neither is part of this design; both remain possible, because applications never see the identity or the controller.

        Rules for applications

        An application that follows these three rules is recoverable by this wallet, and by any other wallet that implements the same scheme, without knowing that recovery exists.

        Rule 1

        Authority is a token

        Whoever may act on a position is whoever spends its ownership NFT in the same transaction. Payouts go to an address the wallet supplied.

        No user key or key hash inside an application contract. A key cannot be replaced; a token can be moved.

        Rule 2

        The wallet's parts are the wallet's business

        The application does not assume the wallet's inputs are P2PKH or have a fixed size. Tokens and change go to an address the wallet names.

        "Back to the address it came from" is acceptable: after a sweep that is a new address.

        Rule 3

        The token leads to the position

        From the NFT alone (its category and commitment) and the template, a wallet can find the position on chain and list the actions it offers.

        No application server and no private note is needed to find a position again.

        Why these are enough

        • Recovery never touches an application contract. The sweep moves the NFT from one wallet address to another. The position stays where it is.
        • The application's transaction layout is its own. The controller is not in application transactions, so an application may fix its input and output positions as it likes.
        • A wallet can recover what it does not understand. An NFT of an unknown application is swept like any coin. Its meaning can be learned later.
        • The rules are checkable. Each can be tested against a contract's source and a template, so a conformance checker is possible.

        What the rules exclude: positions opened by a key written into the contract, positions whose owner is known only to a server, and front ends that insist on building the transaction themselves from the wallet's public keys.

        Template extension

        An XO template describes an application's roles, actions, transactions, inputs, outputs and scripts, and the engine builds every transaction from it. Two things are missing for recovery: a way to say that an output is locked by whatever address the wallet chooses, and a way to say what a token means. The fragments below are sketches. The field names are proposals; they have not been checked against the XO schema or discussed with its authors.

        1. An output the wallet locks

        "outputs": {
  "jarKeyOutput": {
    "name": "Jar key",
    "description": "The token that opens this jar. Keep it in the wallet.",
    "lockingScript": { "wallet": "receive" },        // a fresh address of the wallet's choosing
    "valueSatoshis": 1000,
    "token": { "category": "$(<keyCategory>)",
               "nft": { "capability": "none", "commitment": "$(<unlockTime>)" } }
  }
}

        A template normally names a locking script for every output. Here it leaves the script to the wallet. The same marker on an input says "any coin of the wallet", with no assumption about its script.

        KindThe wallet supplies
        receiveA fresh ordinary address, for a coin or token created now
        changeA fresh ordinary address for what is left over
        returnThe address of a named input of the same transaction, for contracts that require a token to go back where it came from
        lastingA vault address, for an address stored now and paid later

        XO's validator rejects properties it does not know, so this form needs XO's agreement. Until then the same is done with what exists: the template declares a variable that holds a locking script, and the request says which kind the wallet is to fill it with.

        ParyonUSD keeps a small sidecar coin next to each loan, carrying the loan key's category. The wallet finds the unspent sidecar with that category; the loan is the output before it in the same transaction. This reading comes from Paryon's borrowing and manage contracts and has not been run.

        4. The wallet's own template

        The wallet is itself described by an XO template. It holds the controller with its four actions, the recoverable address as a locking script with two unlocking scripts (spend and sweep), the vault address, and a sweep action whose first input and output are the controller.

        Tying a token to a template without a backup. The backup keeps one line per token saying which template made it. If the backup is gone, the wallet can test a token against a template the user trusts: rebuild the position's address from the token and look for that address in the transaction that created the token.

        Talking to applications

        WizardConnect gives an application and a wallet an encrypted channel, started from an address the application shows as text or a QR code. What travels over it depends on what the wallet offers when it connects.

        Who builds the transaction

        The ordinary flow cannot serve this wallet. It hands the application the wallet's public keys, and the application derives P2PKH addresses from them and builds the transaction itself. This wallet's addresses are scripts that cannot be derived from public keys alone. The live front ends of Moria and ParyonUSD, read on 16 November 2026, both refuse any wallet address that is not P2PKH, over WalletConnect as well.

        The xo_v1 extension

        A wallet announces the extension in the WizardConnect session. Nothing in it names an application.

        Rules the wallet follows

        • An unknown template is shown to the user with its name, description and actions, and is trusted only on their word.
        • The user sees two things before approving: the action in the template's words, and the wallet's own figures from the transaction it built. The application cannot influence the second.
        • A request is carried out at most once. It is identified by its id; a repeat gets the stored outcome.
        • The application is never told the identity. It learns the addresses that appear in its own transactions and nothing else.
        • A position is a token. The wallet answers a positions request from the NFTs it holds on chain.
        • The wallet signs with the address keys. The controller is not part of an application's transaction.
        • A token that carries authority is spent only in transactions the wallet built itself from a template the user trusts. Whoever gets such a token spent in a transaction of their own shape can use its authority.
        • A template that breaks one of the three rules is pointed out where the wallet can tell, with what that means for recovery.

        This is the part that most needs XO. XO has invitations and a sync client but no protocol between a website and a wallet. A standard would best come from XO, or as a WizardConnect extension that both projects agree on.

        Savings Jar

        The demonstration application. A jar holds savings until a date. Anyone can pay in. After the date, whoever holds the jar's key NFT can empty it. The jar's contract knows nothing about wallets, keys or recovery.

        contract SavingsJar(bytes32 keyCategory, int unlockTime) {
    // Deposits are ordinary payments to the jar's address.
    function withdraw(int keyInput) {
        // Opens for whoever spends the jar's key NFT in this transaction.
        require(tx.inputs[keyInput].tokenCategory == keyCategory);
        require(tx.time >= unlockTime);
    }
}
        • The key. Opening a jar creates one NFT of a fresh category and sends it to the wallet. Its commitment is the unlock time.
        • The jar's address follows from the key alone: P2SH32( SavingsJar(key.category, key.commitment) ). That is rule 3.
        • One contract for every wallet. An ordinary wallet holds the key NFT at a P2PKH address and the application builds the transaction. Grandma's Wallet holds it at a recoverable address and builds the transaction itself. The jar cannot tell the difference.
        The jar's transactions

          The jar trusts the category. Only the transaction that opens the jar can create tokens of it, and the wallet builds that transaction from the template with exactly one NFT. A wallet that made two keys for one jar would only have two keys to its own jar.

          What this asks of the wallet: it must carry out template actions that create a token. Creating a category needs a wallet coin that is output 0 of its transaction, so the wallet may first have to make one by paying itself.

          ParyonUSD

          ParyonUSD lends its dollar token, PUSD, against BCH collateral. Each loan is managed by whoever holds its loan key NFT. That is rule 1 already, on chain, in contracts that need no change. The plan is a front end and an XO template of our own for it, and a real loan surviving a recovery on Paryon's chipnet deployment.

          A loan, from the wallet's side
            Rule 1 · AuthorityMet

            The loan key is a bearer NFT. The borrowing contract checks its category and amount and not where it is sent.

            Rule 2 · Wallet's partsContracts yes, front end no

            The five contracts read put no condition on the wallet's script. Managing a loan requires the key to go back to the address it left, which is the return kind. The official front end accepts P2PKH wallets only.

            Rule 3 · Finding the loanTo be written

            The sidecar coin carries the loan key's category, so the loan can be found from the key. The template that says so is ours to write.

            What was checked, and what was not

            Checked

            • Paryon's test deployment chipnet-fast-periods-6 answered on 17 November 2026 with 4 active loans and an oracle price of $274.4.
            • Sources of Borrowing, LoanKeyFactory, LoanKeyOriginEnforcer, LoanKeyOriginProof and manage, from the npm package @paryonusd/contracts 1.1.0. The layouts in the diagrams are taken from them.
            • The minimum loan is 100 PUSD at 110% collateral, about 0.4 BCH at that price, plus a 0.25% fee.

            Not checked

            • Nothing has been sent. No loan was opened from a script address.
            • Whether an XO template can express a transaction with four Paryon contract inputs and seven fixed outputs, with the wallet supplying only its own parts. This is the main risk, and it is the claim the demonstration is meant to prove.
            • The other 21 contracts (interest, redemption, liquidation, staking) were not read for this purpose.
            • Paryon's transaction-building library is not public. Ours is written from the contracts.

            Before any front end: open, manage and close one loan on chipnet from a recoverable address with a plain script. That settles whether the contracts accept this wallet. It needs about 0.5 test BCH. Paryon's contracts repository states no licence, so the npm package is used as a dependency and not copied, and telling the Paryon team would be sensible.

            One consequence for privacy: managing a loan returns the loan key to the address it left, so the key stays at one address for the life of the loan. That address is known to anyone who looks at the loan, and to nobody as part of this wallet.

            Backup and self-recovery

            What a recovery depends on

            InformationNeeded forIf it is lost
            IdentityEverythingThe recoverer cannot act. It is in the kit.
            Viewing keysFinding coins and showing their secretsCoins cannot be found or swept. This is the one thing that must not be lost.
            An application's templateShowing what a token means and using its positionThe token is still swept and safe. The template can be had again from the application.
            Which template made which tokenConvenienceThe wallet can test a token against the templates the user trusts.
            LabelsConvenienceNames are lost.

            No record per payment or per address is needed, which keeps the backup small. Backup stores hold sealed copies and cannot read them. The recoverer can read them, so a record counts only if it is signed by the key the controller shows as owner at the time. After a recovery the new device starts a new backup, because the lost phone knows the key of the old one.

            A backup the user keeps

            The design does not need one and supports one.

            • What to keep: the twelve words and the wallet's identity (64 characters). A device with both is the same owner. It recomputes every key and address, finds its coins by scanning, and needs no controller transaction and no waiting period.
            • It is not a standard wallet backup. The words alone restore nothing in another wallet, and nothing here without the identity.
            • It goes stale at a recovery, because the wallet then has a new seed. It must be made again.
            • Whoever holds it has the wallet at once. The waiting period guards against the recoverer, not against someone holding the words.

            Being your own recoverer

            The recoverer's role is a key and the viewing key. Nothing requires a business: a second device of the user's, or a family member's phone, can hold the kit. A wallet has one recoverer at a time, and the owner can replace it.

            Design choices

            ChoiceAlternativeWhy this way
            The controller stays out of everyday transactionsEvery spend passes through the controller, so a key change takes effect at once and nothing has to moveThat alternative puts one coin into every transaction of the wallet. All activity becomes linkable, only one action can be in flight, two such wallets cannot share a transaction, and every application has to make room for the controller at a fixed position.
            Authority is a tokenThe application's contract names the wallet's identity and checks the controller itselfThe application would have to know this scheme and carry its code. A token is something existing applications already use, and it moves with an ordinary transfer.
            The wallet builds the transactionThe application builds it from the wallet's public keys and the wallet signsThe application would have to understand the wallet's scripts. With a template the wallet knows what it is signing and the application needs no knowledge of the wallet.
            One address per coin, identity hidden in a tagOne address for the whole wallet, with the identity in its scriptA single address makes the wallet as traceable as an account number. The tag costs one hash and one secret per address.
            The recoverer keeps the viewing keyThe new device finds addresses from public data aloneAddresses that can be found from public data can be found by everyone. The recoverer is already trusted with the wallet's future.
            Readable controller stateA hashed stateThe state is shown whenever the controller is used. A key per wallet for the recoverer removes the one field that could link wallets.
            A vault address beside the ordinary onesOnly key-bearing addressesSome payments arrive long after the address was given out. A key-bearing address goes stale at recovery; a vault address does not.

            Parts, in the order they depend on each other

            1. Trials with the XO engine: whether it can hold one address per coin with a counter, and carry a sweep.
            2. The controller and ownerApproves. These exist.
            3. The recoverable address and the vault address. Contracts and tests: both paths, the sweep, and every refusal shown on this page.
            4. The wallet's keys. Seed, address chain, viewing key; receiving and paying.
            5. The recoverer. Recovery kit, request, completion; the owner's monitor and cancel.
            6. The sweep on a new device. Finding addresses from the viewing key; moving coins and tokens.
            7. Applications. The xo_v1 extension; building from an application's template; actions that create tokens.
            8. Savings Jar, with its template and recovery declaration, checked with this wallet and with an ordinary wallet.
            9. ParyonUSD. First a loan from a script address by plain script. Then the template and the front end. Then the recovery of a live loan.
            10. Two short specifications for XO: the recoverable address, and the three application rules as a template profile.

            The stages, and what must hold before each is done, are in IMPLEMENTATION_PLAN.md.

            Costs and open points

            Costs of the design

            • An earlier seed works until the sweep. Someone who later finds the lost phone can take a coin that was not swept. The new device sweeps as soon as recovery completes.
            • Payments to an earlier address. A coin sent to an old address after recovery can be moved by the new owner through the controller, and also by the earlier seed. People who pay the wallet need a new address, or a vault address, which does not go stale.
            • The recoverer can read the wallet. The viewing key shows every address and balance. It gives no power to spend.
            • The viewing key is needed to recover. Without it the new owner cannot find the addresses or show their secrets. It is kept by the recoverer and, sealed, in the backup stores.
            • A recovery is public. The sweep ties together everything the wallet held.
            • A request is not cancelled by ordinary use. The owner's device has to notice it and cancel.
            • Larger transactions. Spending a script address costs more bytes than P2PKH: about twice per input, by an estimate from the script size.
            • The first coins are traceable. They can be followed to the creation of the identity.
            • Applications have to be reached through a template. Front ends that build transactions from the wallet's public keys cannot serve it.

            Open points

            • The key paths. One constant is still to be fixed, and it is not known whether the XO engine can use a simple counter for address keys.
            • Who makes the recoverer's key. The owner's phone by default; the recoverer could make it instead.
            • Template fit for large application transactions. Untested for ParyonUSD, see above.
            • The template extension. Whether "the wallet's own address" and the recovery declaration belong in the XO schema or in a companion document is for XO to say.
            • Application state that is not on chain. Accounts opened by signing a message with a key, or state kept on a server, are outside these rules.
            • Positions that change without the wallet. A liquidated or redeemed loan leaves the wallet holding a key to nothing. The template's way of finding the position has to cope with "not found".
            • The extended public key and a leaked address key. As in any HD wallet, the two together give every key of the chain. The viewing key must stay away from anyone who could also obtain one of the wallet's private keys.
            • None of this is audited.
