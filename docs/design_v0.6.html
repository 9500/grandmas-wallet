Grandma's Wallet

A Bitcoin Cash wallet whose keys can be replaced by a trusted recoverer after a public waiting period. Every coin has its own address and key, as in an ordinary HD wallet. A single controller on chain can release any of them to a new owner. Applications give authority to a token in the wallet, and the wallet keeps a record of each position in its sealed backup, so an application position comes back with the token after a recovery.

What changed from design 2

Design 2 is described on its own page, the overview v0.5. Design 3 keeps its keys, its addresses, its controller and its recovery flow unchanged. What changes is how an application's position comes back after a recovery.

Design 2
  • An application brought two documents: its XO template and a recovery declaration written for this wallet.
  • The declaration told the wallet how to fill each action and how to find a position again on chain.
  • A contract had to keep its values on chain, and someone had to write down where.
  • A template was judged as a whole.
  • A recovered ParyonUSD loan could be closed from the wallet with the loan page not opened.
Design 3
  • An application needs nothing but its XO template, written as for any XO wallet. The declaration is retired.
  • Three things carry every action: the template, the application's request, and the wallet's own position record, stored in its sealed backup before anything is signed.
  • After a recovery the new phone reads the records. A record counts only when the chain ties it to a token the wallet holds.
  • Each action is judged by what it leaves behind: it comes back, it does not, or the wallet cannot tell.
  • The wallet acts by itself only where nothing is missing. A loan is closed through its page: "Open the application to do this".

The design

Every ordinary address of the wallet can be spent in two ways. Its own key spends it directly, like any single-key address. The wallet's controller can also release it, and the controller obeys whoever owns the wallet's identity today. Recovery changes the owner of the identity. The new owner then moves every coin and token to addresses of its own keys.

Two ways into every coin

The parts

Wallet

Controller. One coin holding the identity NFT. Its state names the owner's controller key, the recoverer's key and the waiting period. It moves only for recovery, sweeps, the vault and changes of settings.

Wallet

Recoverable addresses. One per coin, each with its own key for every day and a hidden link to the identity for recovery. A second kind, the vault address, has no key and never changes.

Recovery

Recoverer and viewing key. The recoverer can replace the owner after the waiting period. It also keeps the viewing key, which lets a new device find every address. Neither lets it spend.

Applications

Two rules, a template and a record. Authority is a token. The wallet's inputs and outputs are the wallet's business. The wallet builds each transaction from the application's XO template and keeps its own record of each position, in the sealed backup.

Identity and controller

The wallet's identity is the token category of one NFT. The coin that holds this NFT is the controller. The NFT's commitment is the controller's state, 69 bytes. The controller's script accepts five actions. Four of them send the NFT back to itself with the next state. The fifth closes the wallet and destroys the NFT.

In every action the signature must cover every input and output. In the four that continue the controller, it is input 0 and output 0 of its transaction, the NFT continues and the coin's value does not shrink.

Closing cannot be undone. A vault address works only while the identity's NFT exists, so after closing nobody can spend from one, and a coin that arrives there later is lost. There is no recovery afterwards. The action is part of every controller so that a wallet can be emptied to the last satoshi; the test runs end this way. See Fees and emptying.

The controller's script does not check its own first state. Before trusting an identity, a wallet checks the transaction that created it (one NFT of the category, no way to make another, a valid first state, locked by the controller script) and follows every step of the controller from there to today.

Two properties carry the scheme

  • The waiting period is enforced by the network. It is a relative time lock on the controller's own coin. Nobody can shorten it.
  • The recoverer's key never spends a coin. A coin released through the controller requires the controller to continue unchanged, with the same owner and no request pending. A request leaves a claim pending and a completion changes the owner, so neither can carry coins with it. This check is one shared function, ownerApproves(identity), used by every address script. A recoverer who installs a key of its own after a wait that nobody cancelled is then the owner; that is the trust placed in it.
function ownerApproves(bytes32 identity) {
    // Input 0 is this identity's controller.
    require(tx.inputs[0].tokenCategory == identity + 0x01);
    bytes state = tx.inputs[0].nftCommitment;
    require(state.length == 69);
    require(state.split(1)[0] == 0x01);
    // It continues as Active with the same owner, epoch, recoverer and delay.
    require(tx.outputs[0].tokenCategory == identity + 0x01);
    require(tx.outputs[0].nftCommitment == 0x0100 + state.slice(2, 49) + bytes20(0));
}

Only an owner-signed step produces that successor: ownerAuthorize, or an ownerUpdate that changes nothing. The owner's signature on the controller, which covers the whole transaction, is therefore what approves the release. The simulator under A wallet's life shows the state byte by byte.

Keys and addresses

The wallet works like an HD wallet and uses the same building blocks: twelve words (BIP39) and a tree of keys computed from them (BIP32). One seed on the phone gives a key for every address, and every coin can sit at its own address. What is added is a second, hidden way into each address, and a viewing key that lets someone other than the phone find the addresses again.

Seedon the phone only
Twelve words, made on the phone. Every key below is computed from them, and nothing random is added later. The user is not asked to write them down. Losing the phone loses the seed.
Controller keyfrom the seed
One key on a branch of its own. Its hash is the owner entry in the controller. On chain it signs nothing else, and it appears in no address. Off chain it signs the wallet's records and its requests to the recoverer.

Blinding seedfrom the seed

T is the template's number, which follows from the template's content: C for the controller template, A0 and A1 for the two address templates, W for XO's standard wallet template. n counts up from 0. Finding everything again

A device that holds the identity and a viewing key finds that seed's coins in two passes. No list of addresses has to be kept anywhere.

  1. Quick pass. For each kind of address it derives number 0, 1, 2 and so on, looks each up on chain, and stops after a run of unused ones: 20 for addresses given out, 5 for change and for vault addresses. This is how any HD wallet is restored, and it nearly always finds everything.
  2. Full pass. It looks up every number of every range. Each kind has a fixed number of addresses per seed, the same for every wallet, so nothing about the ranges has to be stored. This finds what the quick pass can miss, for example an address given out past a gap after the transaction that had closed the gap was dropped.

For each address it finds, the device also has the secret, which is what the recovery path needs. The wallet is reported as fully found only when the full pass has finished for every seed it has had. A server that does not answer gives "incomplete", never "empty".

After a recovery the new device has a new seed and a new viewing key. It gives the new viewing key to the recoverer before the request is made, so the wallet is never without a recovery path. The same holds when an owner moves to a new seed with the old phone at hand: the recoverer confirms that it holds the new viewing key, and only then does the owner key change. Earlier viewing keys are kept: they find payments that still arrive at earlier addresses.

Creating a wallet: whoever has the coins creates it

An address needs the identity, and the identity is the identifier of a transaction, so a wallet's very first coins cannot arrive at a recoverable address. The phone does not fund its own creation: the recoverer does, from its own coins. A bank gives a new customer a small starting balance as part of its service; a friend or family member gives the person they help their first coins. Both pages are open at the same moment, in person or on a call.

  1. Scan and ask. The phone scans the recoverer's code, makes its keys, and stores its viewing key in its new backup. Once a store has confirmed, it sends a sealed, signed request over the session the code offers: an identifier, its controller key's hash, its viewing key, the access to its backup, the waiting period it was told, and the number of its address for the starting balance.
  2. Create. The recoverer creates the wallet from its own coins, paying itself first when it has no coin that is output 0 of its transaction. One transaction: the controller naming the owner's key, the recoverer's own key and the waiting period; the starting balance at a change address of the new wallet; the rest back to the recoverer's balance. A bank's page creates without anyone saying yes; a friend's page asks "Set up …'s wallet with …?" first.
  3. Keep and answer. The recoverer assembles the kit from the request and what it created, keeps it, leaves its receipt in the phone's backup, and answers with the identity, the creating transaction and the hash of its key.
  4. Check and open. The phone checks the creation as any client does, and that it names its own key, the recoverer that answered and the waiting period it was told. Then it shows "Your wallet is ready", with the balance and "Protected by …".

A request is carried out once: the phone sends the same request again until it has its answer, and the recoverer's page keeps every request and every step, so a reload on either side, or an answer that is lost, gives the same wallet, never a second. The first transaction is trusted. The recoverer could refuse, or create a wallet the phone refuses; it cannot make the phone accept one that names another owner, another recoverer or another waiting period.

Nothing waits for a block. The phone goes on as soon as the network has the creation; the starting balance can be spent at once. This is safe for ordinary addresses because each has two ways in: its own key, which does not involve the identity, and the controller. If the creation were replaced or a block that held it were undone, the coins already paid to them would still be spent by their keys. Only their recoverability would be gone until they are moved. A vault address has no key. It is given out from the first moment as well, and a payment to one would be lost with the creation; that was weighed against making the user wait, and accepted.

So the wallet watches the creation until a block holds it. If it disappears, the set-up did not hold: the wallet says so plainly on its first screen and is set up again with the recoverer. It makes no identity of its own. It keeps the addresses it gave out, numbers the new ones past them, and once it is set up again moves what arrived at the earlier ones to the new wallet with ordinary key payments.

Every address is built in the same steps. Choose a kind and a number to follow them for one example wallet.

number 0

  • The phone can do every step. A holder of the viewing key can do all but the private key: it gets each public key from the extended public key.
  • Nobody can go backwards from an address. The address is a hash of the script. The tag inside the script is a hash of the identity and a secret that only the viewing key gives.
  • Two addresses of one wallet share nothing visible. Each has its own key and its own secret, so each has its own tag.
  • The payer sees an ordinary script address. Nothing shows that it is recoverable or which wallet it belongs to. Spending it by key shows the kind of address, and still not the wallet.
  • The wallet stays inside a window and a range. It shows no address more than 20 numbers past the last used one of its kind (5 for change and for vault addresses), and none past the fixed range of its kind. When the window is full it offers an address it has already given out, and says so.
  • An address made for something that did not happen gets its number used again only if it was never shown and nothing was signed. Otherwise it stays taken and stays watched.

The recoverable address

A script address (P2SH32) with two ways to spend.

contract RecoverableAddress(bytes32 tag, bytes20 keyHash) {
    // Everyday path: the key this address was made for.
    function spend(pubkey pk, sig s) {
        require(hash160(pk) == keyHash);
        require(checkSig(s, pk));
    }
    // Recovery path: whoever owns the identity today, through the controller.
    function sweep(bytes32 identity, bytes32 addressSecret) {
        ownerApproves(identity);
        require(hash256(identity + addressSecret) == tag);
    }
}

contract VaultAddress(bytes32 tag) {
    // No key. Only the identity's current owner, through the controller.
    function spend(bytes32 identity, bytes32 addressSecret) {
        ownerApproves(identity);
        require(hash256(identity + addressSecret) == tag);
    }
}

Compiled, the rules are 96 bytes for the recoverable address and 75 for the vault address, before the tag and the key hash are added. Measured in a trial, an input spent by its key is 296 bytes, a swept input 260 and a vault input 217, against 141 for an ordinary single-key input. The contracts' tests hold these figures.

Recoverable address

The wallet's ordinary address, a fresh one for each coin, token and change output. Used for everything the wallet does with applications. After a recovery its contents are swept to addresses of the new seed.

Vault address

For an address that must outlive a key change: one published to be paid at any time, or a payout address agreed long before the payout arrives. It is meant to be used more than once. Spending from it needs the controller at input 0, so a token is moved from the vault to an ordinary address before an application can use it.

      Fees and emptying

      The wallet pays the lowest fee that nodes relay, and works it out from the transaction itself.

      • The rate is one satoshi per byte, which is what nodes require. It is fixed in the software and is not a setting on a screen; the wallet does not raise it by itself.
      • The fee is exact. It is the size of the signed transaction times the rate. The size is known before signing, because signatures, keys and scripts have fixed lengths: the wallet adds up exact sizes, not estimates.
      • The smallest output depends on the output. Nodes relay nothing below 546 satoshis at a single-key address, 576 at an address of this wallet, 888 for the controller, and more for an output with a token. The wallet computes this for every output it creates.
      • Change is what can be saved. Every coin costs its bytes once, whenever it is spent. A change output costs bytes now and again when it is spent, so the wallet prefers a choice of coins that needs none.
      • Nothing goes to the fee unseen. If what is left is too small to return as change, the wallet compares leaving it to the fee with adding a coin, takes the cheaper, and shows the amount.
      • A check before sending. The signed transaction must pay the fee its actual size requires and less than a change output's worth (576 satoshis) above it, hold no output below its smallest value, and pass every script in the virtual machine. There is no other limit on the fee in satoshis, which would stand in the way of a transaction with many inputs.

      Sending everything

      • What goes: every coin without a token, to one address. There is no change, and the amount is the total less the exact fee. A coin worth no more than the bytes it costs is left out and listed. A very large wallet takes several transactions of at most 100,000 bytes.
      • Coins that only the controller can move, at vault addresses or at an earlier seed's addresses, go in the same transaction with the controller.
      • Satoshis under a token stay with the token. They leave when the token is sent, or when the user destroys the token on purpose.
      • It cannot be done only when the total less the fee is below the smallest output. A single coin of 576 satoshis leaves 236 after its fee of 340, which cannot be sent. The wallet then shows the total, the fee and the smallest output.
      • What is left: the controller, coins with tokens, and whatever the recoverer holds. The wallet stays usable and recoverable. Until it holds Bitcoin Cash again it cannot pay for a cancellation.

      Receiving and sending tokens

      • Every address can hold tokens. Its token-aware form (z… or r… after the prefix) pays the same script; it is the receiver's word that its wallet knows tokens. The Receive screen shows it first; unticking "Receiving a token?" shows the plain form.
      • An amount, or one NFT. A fungible token is one balance per category; the wallet gathers its coins, the largest first and leaving alone those that also carry an NFT, and the rest comes back to a fresh change address. An NFT goes whole, commitment and capability unchanged, with any amount on its coin.
      • The fee from ordinary coins. Each token output holds the smallest value it may; what the token coins held beyond that comes back with the change in Bitcoin Cash.
      • Only to a token-aware address. A plain address is refused before anything is built: a wallet that does not know tokens can destroy them.
      • A token that gives more than itself (a key to a position, an NFT that can mint or be changed) is sent only after the review says what it gives and the user ticks that they understand.

      Closing

      Sending everything with ownerClose in the last transaction also takes the controller's value and ends the identity. Measured at one satoshi per byte:

      MeasuredResult
      Closing with no other coin1,000 − 681 = 319 satoshis, below the smallest output: it cannot be sent

      Closing is therefore the last step of emptying a wallet, never a step of its own. A sweep or a vault spend cannot be part of it; what only the controller can move is moved first. The wallet's ordinary interface does not offer it. A library function does, which the test runs use; it refuses while a vault coin, a token or an unswept coin at an earlier address is held, or before the full search has finished. Whoever holds the owner's key can also build the transaction without this software. The recoverer cannot close.

      Recovery flow

      1. 0

        Setup, while all is well

        Owner and recoverer

        The phone scans the recoverer's code and asks; the recoverer creates the wallet from its own coins, naming the phone's key, its own key and the waiting period, keeps the kit and leaves a signed receipt; the phone checks the creation and opens its wallet. Recovery is on once the wallet finds the receipt, which is already there.

      2. 1

        A new device asks

        New device and recoverer

        The recoverer presses "Customer lost their phone", or "… lost their phone", and its page shows a code. The new phone chooses "I lost my phone" and scans it. It makes a new seed and gives the recoverer, over the session of the code, the hash of its controller key, its own viewing key signed with that key, the access to a new backup, and a key for the answer. It does not need to know the wallet's identity yet. The recoverer satisfies itself that the person is the wallet's user before it shows the code; how it does so is its own process, and the design depends on it.

      3. 2

        Request

        Recoverer

        The recoverer's page signs requestRecovery naming that key as soon as the request arrives on the lost phone's code. A request that comes another way, as a link or on a set-up code, waits in the page's list until the recoverer has made sure who is asking and chosen the wallet. The controller is then Pending, on chain. The owner's wallet sees the request and warns at once; the waiting period counts from the block that holds it.

      4. 3

        Wait, and the owner's chance to refuse

        Owner, if the phone is not lost

        The wallet watches its controller on several servers. If a request appears that the owner did not ask for, the owner cancels it with one signature of the controller key. Ordinary payments do not touch the controller, so they do not cancel a request. The cancel is a transaction of its own, by hand or, unless the user turns that off, automatically while the wallet's page is open. Any transaction of the owner that carries the controller, such as a sweep, cancels as well. The fee of about 1,100 satoshis comes from the wallet's coins. A wallet that holds only tokens says on the warning that it needs a little Bitcoin Cash to refuse, and where to receive it.

      5. 4

        Complete and hand over

        Recoverer

        After the waiting period the recoverer signs finalizeRecovery. The proposed key becomes the owner and the epoch goes up. No coin has moved. As soon as the network shows the completion, the recoverer gives the new device the identity, the viewing key of every earlier seed and the access to earlier backups, sealed to the device: over the session of the lost phone's code when both pages are open, otherwise as a code the new phone scans. The new device sweeps and gives out addresses.

      6. 5

        Sweep

        New device

        With the identity and the earlier viewing keys the new device finds every address in use: a quick search first, then a full search of every range. It moves what is there to addresses of its own seed, in transactions that carry the controller, signed with ownerAuthorize. Each swept input shows the identity and its address secret. Coins, fungible tokens and NFTs move the same way. The fee comes out of the swept coins. A large wallet is swept in several transactions: every coin with a token first, understood or not, then the others by value.

      7. 6

        Understand what the tokens are

        New device, with the applications' templates

        A swept NFT is already under the new owner's control. To show it as "a jar with 0.3 BCH that opens in March" the wallet needs the application's template and its own record of the position. It reads the position records of the earlier backup, checks each against the chain (The chain as the check), and hands the scripts of those that count to the XO engine, with their values. A template from an earlier owner's backup is a suggestion: the user trusts it again before the wallet acts on it. A token without a record is listed as a token, and the wallet does not search for what it controls. Recovery does not wait for this.

      8. 7

        Keep watching

        New device

        The new device watches the controller, and it follows the earlier addresses it found in use for payments that still arrive there. Its coins pay for refusing a request, as on any device. See A payment to an old address.

      The recovery kit and the recoverer's key

      • The kit contains the identity, the recoverer's credential for this wallet, the viewing key of every seed, where the sealed backups are kept and how to read them, and the settings, for the recoverer to compare with the chain. The recoverer assembles the first kit itself, from the phone's request and the wallet it created, and adds to it whenever the wallet gets a new seed.
      • One scan, both pages open. The recoverer's page shows one QR code that holds its name, its key and the address of a WizardConnect session it keeps open while it is shown. The phone scans it, and everything else goes over the session: the set-up request and its answer, a lost phone's request and the hand-over. A code scanned from the bank's page or a friend's screen is a trusted channel: for these there is no fingerprint to compare and no invitation answered hours later. Moving to a new phone with the old one at hand, and changing the recoverer, still use sealed links and a fingerprint compared over another channel; the kit for a new recoverer can also go over its session.
      • One page, two ways of working. "I'm a bank": "New customer" shows an activation code and the wallet is set up the moment the phone asks, with nobody saying yes; a list of customers; "Customer lost their phone". "I'm helping someone I know": "Help someone set up" asks who and shows the code, then "Set up …'s wallet with …?" and one tap. Both show the recoverer's balance and an address to fund it, and settings for the starting balance and the waiting period, which the wallet shows as a fact.
      • The recoverer's key is one per wallet, not one per coin. Only its hash is on chain, in the controller. No address contains it, and the recoverer never signs for a coin of the wallet. It signs two kinds of transaction: the request and the completion.
      • The recoverer uses a different key for every wallet, so the controllers of two wallets with the same recoverer show nothing in common. The recoverer makes this key as a set of twelve words of its own when it creates the wallet; the phone never knows it. (A phone that replaces its recoverer still makes the new one's words, as before.)
      • The recoverer pays its own fees, about 2,000 satoshis for a request and a completion, from its one balance, the same that it creates wallets from. A request, or a completion, is one transaction: the wallet's controller, unlocked with the recoverer's key for that wallet, and a coin of the balance for the fee, with the change back to the balance. Nothing is kept apart for a wallet, and the whole balance can be sent to another address. The owner gives the recoverer nothing: the allowance of earlier versions is dropped. What it shows on chain: the wallets a recoverer has created or acted for share its balance as their payer.
      • A receipt decides. The wallet says that recovery is on only when the recoverer's signed receipt matches what it was sent and the controller's state on chain.
      • A new seed with the old phone at hand, and a new recoverer, follow one order: the recoverer first confirms that it holds what it needs, and only then does the owner sign the change. A recoverer that is replaced keeps what it has already seen.

      The recoverer of this project is a page on the XO engine. Nothing in the design requires that. A recoverer is whatever does three things:

This design builds no second recoverer; it states the role so that one can be built without changing the wallet.

      What the waiting period does and does not protect. It protects against a recoverer who acts without being asked, as long as the owner notices in time. A recoverer who names their own key and is not cancelled gets the wallet. It does not protect against a thief who can use the owner's phone: such a thief can spend at once, as with any wallet.

      If a recovery completes against the owner's will, the owner's keys still spend every coin that has not been swept. A wallet that finds itself owned by a key it does not hold stops giving out addresses, makes sure of what it sees on more than one server, and offers to move its coins out at once, to an address the user enters: one of another wallet that does not share this wallet's recoverer. That is a race against the new owner's sweep. Coins at vault addresses cannot be saved this way.

      What still waits for a block, and why

      Everything that can go on before a block does. A transaction that disappears later takes with it only what was built on it: the wallet follows the chain at every check, and coins at addresses of a device stay that device's by key. Three things wait, each for a reason that cannot be designed away:

      • The waiting period of a recovery counts from the block that holds the request. It is a time lock that the network enforces, and a transaction that is not in a block has no age yet. The period is the owner's whole protection, so it is measured by the chain and not by a clock anyone could claim. The owner's wallet shows the request and warns as soon as it is seen; only the count starts with the block.
      • A phone stops for good only when a block holds another owner. The moment the network shows another key as the owner, the phone gives out nothing and takes on nothing. A completion that is not in a block can still lose to the owner's cancellation, so until a block holds it the phone only pauses, and carries on by itself if the change disappears.
      • Time locks of applications, such as a savings jar's date or a loan's periods, belong to their contracts, not to the wallet.

      A payment to an old address

      After a recovery, someone may still pay an address the wallet gave out before: an old invoice, an address saved in an exchange's withdrawal list. That coin is not lost. The new owner collects it through the controller, by the same path as the sweep. This is not the vault address; the two are compared below.

      1. The coin lands at the old address. Receiving runs no script, and nothing on chain tells the payer that the wallet has a new owner.
      2. The new device notices it. It holds the earlier viewing key, which the recoverer handed over. From it the device derives the same addresses the old phone used. It is to keep watching every address that was used and the window past the last one, and to look up the whole range again from time to time. Today it searches once, on arrival, and then follows the addresses it found in use (not yet built).
      3. The new device collects it. One transaction: the controller at input 0, approved by the new owner, and the coin, unlocked by showing the identity and that address's secret. The secret comes from the earlier viewing key. The coin goes to an address of the new seed. The wallet shows such a coin, and the user moves it with one tap.
      4. Until then the coin has two masters. The key the address was made for is on the lost phone, and it still opens the address. This matters only if someone can use that phone.

        The controller is readable on purpose

        Anyone can see that a controller exists, and read its state. Its state names no address. Hiding the state behind a hash would gain little: every transaction of the controller has to show the state to the script, so it would become public the first time the controller is used. Two simple measures do more:

        • The recoverer uses a different key for every wallet. Two wallets with the same recoverer then show nothing in common.
        • The owner's controller key signs nothing else on chain. It never appears in an address.

        What a recovery reveals

        A sweep has the controller as its first input and shows the identity in every swept input. Everything the wallet held at that moment is tied together, in public. Coins received afterwards at new addresses are not, until they are spent together with coins that are. A token whose history is public, such as a loan key, links its position before and after the sweep.

        Limiting this would take several controllers, each covering part of the addresses. Hiding it fully would need a way to prove the link without showing it, which this project has not found for Bitcoin Cash and does not claim. Neither is part of this design. A later version of the wallet's scripts could add either without changing applications, because applications are never sent the identity or the controller and deal only with tokens.

        Rules for applications

        An application that follows two rules can be used with this wallet and comes back after a recovery. It does not have to know that recovery exists, and nothing has to be written for this wallet. Both rules are properties of the contract and of how its template is written for XO.

        Rule 1

        Authority is a token

        Whoever may act on a position is whoever spends its ownership NFT in the same transaction.

        No user key or key hash inside an application contract. A key cannot be replaced; a token can be moved. A token its holder can copy moves the authority without taking it from an earlier holder.

        Rule 2

        The wallet's parts are the wallet's business

        The application does not assume the wallet's inputs are P2PKH or have a fixed size. What the user receives goes to a script that the user's role provides.

        In an XO template: the output's locking script is a variable the user's role has to provide. "Back to the address it came from" is acceptable: after a sweep that is a new address.

        The wallet's job

        Finding the position again

        The wallet keeps a record of every position it makes, in its sealed backup, and the chain confirms the record.

        Design 2 made this a third rule for applications: the token had to lead to the position on chain. An application's contracts now keep their values where they like.

        Why these are enough

        • Recovery never touches an application contract. The sweep moves the NFT from one wallet address to another. The position stays where it is.
        • The application's transaction layout is its own. The controller is not in application transactions, so an application may fix its input and output positions as it likes.
        • A wallet can recover what it does not understand. An NFT of an unknown application is swept like any coin. Its meaning can be learned later.
        • Liquidation, vesting, repayment and the application's other conditions are untouched. Recovery restores the remaining rights, not an earlier state.
        • Part of this can be checked by a program. Whether an action leaves something at a script that takes a key of the device, and whether the user's outputs are left to the user's role, the wallet sees from the template and from the transaction it builds. Whether a contract gives authority to the token and to nothing else takes reading the contract and testing it.

        Excluded for good: positions whose owner is known only to a server, including accounts opened by signing a message, and front ends that insist on building the transaction themselves from the wallet's public keys.

        Position records

        For every script it follows, the XO engine keeps what the script was made with: the template, the locking script, the role and the values. It keeps this in the storage of one device, under one account, and an account belongs to one seed. A recovery replaces the seed. A position record is a copy of that state, made by the wallet's own code from the transaction it has worked out, and stored in the sealed backup before anything is signed. The new phone reads it, the chain confirms it, and the engine follows the script again.

        Written before anything is signed

        A record is due when an action leaves an output at a script of the template that the wallet follows and a token of the wallet's takes part, or when an action delivers an application's NFT to the wallet. The wallet writes it from the transaction as built, and a backup store has to confirm it before a signature leaves the wallet. If no store confirms, this wallet refuses the action; another wallet may go on and show the position as not yet backed up.

        A store that cannot be reached does not stop ordinary use. Paying, receiving, and actions that leave nothing behind go on. It stops only what would create a new dependency: the first action of a new template, and an action that leaves a position. Design 2 could let such an action go on without a store, because it found positions again from the chain. Without a declaration there is no second way.

        After a recovery the new phone copies the earlier backup's records into its own new backup as suggestions, and writes each again as its own once the chain has confirmed it. The new engine holds only what it was given.

        The chain as the check

        A record is a hint, never an authority. Each record is signed by the controller key of the seed that wrote it. After a recovery every record is one of an earlier seed, and whoever holds that seed can still sign new ones. So what makes a record count is the chain, not its signature.

        A record counts when all of these hold:

        1. The wallet holds the record's NFT, and the user trusts the record's template.
        2. A transaction on chain carried that NFT, and also paid the script that the template, the record's locking script and the record's values give.
        3. That NFT is the one the wallet holds: category, capability and commitment are compared, never the category alone. Where the token could have been copied, because it can mint or its commitment can change, the wallet follows it back from its own coin, input by input. If the way back is not unambiguous, the record does not count.
        4. Where the template names the token as an input of an action, the values that input uses are the token's own. A record that gives the script another key's category does not count.

        The check rests on rule 1. Whoever acts on a position spends its token in the same transaction, so a transaction that made or moved a genuine position carried the token. Someone who does not hold the token cannot make such a transaction. The wallet looks from the script's side, among the few transactions that paid it; in the run of stage 17 the check cost one history and one transaction from the server.

          A template says, for each action, which variables the wallet's role has to provide. The wallet fills each from the first of these that applies.           What an action leaves behind

          The wallet judges actions one by one, from the template alone, before anything is planned, stored or signed.           Comes back

          Nothing is tied to the phone

          A key of the device

          The action leaves something at a script that takes a key the engine makes for the wallet under the application's template. That key is lost with the seed.

          Talking to applications

          WizardConnect gives an application and a wallet an encrypted channel, started from an address the application shows as text or a QR code; the wallet page reads such a code with the phone's camera. What travels over it depends on what the wallet offers when it connects.

          Who builds the transaction

          The ordinary flow cannot serve this wallet. It hands the application the wallet's public keys, and the application derives P2PKH addresses from them and builds the transaction itself. This wallet's addresses are scripts that cannot be derived from public keys alone. The live front ends of Moria and ParyonUSD, read on 16 November 2026, both refuse any wallet address that is not P2PKH, over WalletConnect as well. An application that wants both kinds of user shows one connection address and decides by what the wallet offers; the Savings Jar does this, and was checked with Cashonize in design 2.

          Rules the wallet follows

          • An unknown template is shown to the user with its name, description and actions, and is trusted only on their word. It is checked against the identifier and content hash the request names, and stored in the backup before anything is signed.
          • The wallet states what it knows about a template, and no more. For a template met for the first time, that is what a program can see: whether a script of it takes a key of the device, and which actions would put something there. It does not call a template verified. Once a position made with the template has come back through a record that the chain confirmed, it says that the template has come back once. An audit of the contract is neither claimed nor implied.
          • Before the user is asked, the wallet works out what the action leaves behind, and carries it out once a store has the record, or refuses with the reason. The application cannot influence this.
          • The user sees two things before approving: the action in the template's words, and the wallet's own figures from the transaction it built: what goes where, what the wallet gives and gets in coins and in tokens, which coins of the application are spent, which tokens are destroyed, the fee and the earliest time. The application cannot influence the second.
          • A request is carried out at most once. A repeat, or a reconnect, gets the stored outcome, and the same id with other content is refused.
          • The application is never sent the identity, a viewing key, or anything about other applications. It learns the addresses that appear in its own transactions.
          • A position is a token with a record. A token without a record is not answered for, and a record without a token in the wallet is no position.
          • The wallet signs with address keys. The controller is not part of an application's transaction.
          • A token that carries authority is spent only in transactions the wallet built itself from a template the user trusts, or sent on by the wallet's own Send after the tick.
          • A standard signing request is refused. The wallet builds every transaction itself.

          XO

          Nothing is required of XO. Design 3 runs on the engine as published. It relies on three things staying as they are: an invitation of one template takes inputs and outputs of other templates; a script can be made known to the engine from its template, locking script, role and values; and a template can leave an output's script to a variable and mark a script as one a wallet need not follow. Design 2 proposed a place in XO's schema for its declaration, a marker for outputs the wallet locks, and expressions that read the coins a transaction spends. None of that is asked any more.

          Where this wallet differs from what XO assumes

          It is not the wallet's script addresses: the engine's default policies let a wallet name any template for its own addresses, and everything here runs on the engine as published. It is that the wallet replaces its seed. XO takes an account to be one seed for good: keys are made for each template from the seed, and the state is kept for each account. A wallet with ordinary single-key addresses that replaced its seed would meet the same three things: keys under an application's template are gone, the engine's state belongs to the earlier account, and a synchronisation tied to the seed cannot be read.

          Asked how a position should come back on another device, XO's authors pointed to carrying state from one device to the next. The position record is that hand-over made ahead of time: the old device is the sender, the store is where it waits, the new device is the receiver. After a loss there is no sender left to make one later.

          The record keeps the engine's field names

          For every script it follows, the engine keeps a ScriptHashData (in @xo-cash/state 0.0.5): the script hash and locking bytecode, the template's identifier, the locking script's identifier, the output and the role, the invitation that made it, and the variables it was made with. The record uses the same names, templateIdentifier, lockingScriptIdentifier, roleIdentifier, variables, so that the transport can change without the wallet's rules changing. XO's synchronisation, which its state package describes and marks as not implemented yet, could carry the records in place of this project's stores if it offers three things:

          1. A key that can be handed on. After a recovery the earlier seed is gone, so a key for the synchronised state that derives only from the seed is lost with it. The wallet has to be able to give it to the recoverer with the kit.
          2. Reading an earlier account's state under a new seed, taking from it only the scripts of applications, not the earlier seed's own addresses and keys.
          3. A confirmation before signing, since no signature leaves the wallet before the record is stored.

          The check against the chain stays whatever carries the records: a synchronised record is a suggestion until the chain confirms it.

          What XO plans for the first of these. An action today results in a transaction or in arbitrary data. XO expects to let an action result in a locking bytecode: an invitation for such an action is started and followed through to its end, and the engine then holds the script, with its follow-up actions. That is the supported form of what the wallet does by hand, and no transaction takes part in it. Such an action is one the template defines; whether a wallet could then follow a script of a template whose author wrote no such action is not known, and for those the wallet's own way would still be needed.

          The wallet's own templates

          The wallet is itself described by XO templates. The engine derives a template's keys from the template's content, so the controller, the addresses given out and the change addresses are three small templates that never change. A fourth, which holds no key and may change, has the wallet's actions, the address of an earlier seed (which can only be swept) and the vault address. XO's standard wallet template is the fifth, for single-key coins such as the recoverer's balance. One transaction can take inputs and outputs of several templates; that is how a sweep carries the controller and the coins, and how an application's transaction takes the wallet's coins. Trials ran this through the unmodified engine on a local node: one script per address with the wallet's tag, a payment by key, a sweep of several coins each with its own secret, and a new seed taking over an identity that another account created.

          Savings Jar

          The demonstration application. A jar holds savings until a date. Anyone can pay in. After the date, whoever holds the jar's key NFT can empty it. The jar's contract knows nothing about wallets, keys or recovery, and it is the same as in design 2.

          • A changed template has a new identifier. Jars opened with the earlier version are emptied with the build of design 2 first.
          The jar's transactions

            The jar trusts the category. Only the transaction that opens the jar can create tokens of it, and the wallet builds that transaction from the template with exactly one NFT. Creating a category needs a wallet coin that is output 0 of its transaction, so the wallet may first have to make one by paying itself.

              A backup the user keeps

              The design does not need one and supports one.

              • What to keep for the current seed: four lines: the network, the address scheme, the wallet's identity (64 characters) and the twelve words. A device with all four is the same owner.               • What that leaves out: addresses of earlier seeds, found only with the earlier viewing keys; and the position records.               • It goes stale at a recovery or a change of owner, because the wallet then has a new seed. It must be made again, and an old backup cannot undo the change.
              • Whoever holds it has the wallet at once. The waiting period guards against the recoverer, not against someone holding the words.

              Costs of the design

              • An earlier seed works until the sweep. Someone who later finds the lost phone can take a coin that was not swept, and a position whose token was not swept. The new device sweeps as soon as recovery completes.
              • Payments to an earlier address. A coin sent to an old address after recovery can be moved by the new owner through the controller, and also by the earlier seed. People who pay the wallet need a new address, or a vault address, which does not go stale.
              • A vault address before the first block. The wallet gives one out as soon as it is created. If the creation then disappears, a payment already made to that address can be spent by nobody.
              • A token that can be copied. Recovery moves a token. Where the holder of a token can make more of it, as with Paryon's loan key, a copy made before the sweep keeps its power.
              • The recoverer can read the wallet, and which positions it holds in which application, with the values each was made with. It gives no power to spend.
              • The viewing key of every seed is needed to recover. The recoverer has to keep each one; sealed copies are in the backup stores.
              • Every position depends on the backup stores. Making one waits for a store, and the wallet finds it again only where a copy of its record is found.
              • A recovery is public. The sweep ties together everything the wallet held.
              • A request is not cancelled by ordinary use. The owner's device has to notice it and cancel, and refusing needs about 1,100 satoshis of Bitcoin Cash.
              • Larger transactions. 296 bytes for an input spent by its key against 141 for P2PKH, as measured.
              • The first coins are traceable to the creation of the identity, and to the recoverer's coins.
              • Applications have to be reached through a template. Front ends that build transactions from the wallet's public keys cannot serve it.
              • This wallet refuses to open a position that a key of the device opens, even where part of that position would survive a recovery.
              • The wallet does not act for an application where an action needs something only the application knows. A ParyonUSD loan is managed through its page.
              • A token that came from someone else is held and can be sent, and the wallet does not find what it controls: there is no record for it.
              • Fungible tokens are shown by category and in raw units, until the wallet reads a token registry. Sending a token such as PUSD is harder to read than in design 2, whose declaration named it.
              • A complete search is a long one. It looks up every address of fixed ranges, for every seed the wallet has had.
              • Templates that hold keys can never change, and an old identity can outlive its rules. Closing makes every controller transaction 45 bytes larger and turns the identity's vault addresses into addresses nobody can spend from.

              Open points

              • Every copy of a record lost, the lost phone's included. The token is still the wallet's, is listed, and can be sent; the wallet cannot find the position. An action the application builds for it is carried out only where the wallet gives nothing but the fee. Having the application name the position for a token without a record, under the same check, is not part of this design.
              • Positions at a script many users share. Their record names no script, so the chain check has nothing to test beyond the token: the record says only "this token belongs to that template". Whether the position is open, the application says.
              • Positions that change without the wallet. A liquidated or redeemed loan leaves the wallet holding a key to nothing, and a record that names a coin which is gone. "Closed" and "not found" are ordinary answers.
              • A record planted before the sweep by whoever holds the earlier seed can be listed as a position beside the genuine one. That holder can take every coin in the same time, so the wallet does not try to keep it out.
              • Token names. Names and decimals are to come from a token registry (BCMR) once the wallet reads one; what such a lookup tells a server about the wallet has to be settled then.
              • XO's synchronisation in place of this project's stores, once it exists and offers the three things listed under XO.
              • Confidence in the chain. What the wallet reads about its transactions and their confirmations it takes from the servers it is set up with, the user's own node among them. It does not call chain state verified.
              • Watching on a phone. A phone that is switched on is not thereby watching the chain. The wallet watches while its page is open, and says so.
              • Both pages at once. Setting a wallet up and asking for it on a new phone need the recoverer's page and the phone open at the same moment. That has been tried in browsers on one machine, not on real phones or through public relays.
              • The extended public key and a leaked address key. As in any HD wallet, the two together give every key of the chain.
              • None of this is audited.

              Designed, not yet built

              • Watching earlier addresses. The design has the new device watch every earlier address that was used and the window past it, repeat the full search, and collect a late coin by itself. The wallet searches once, when it arrives on a device, and then follows only the earlier addresses it found in use.
              • Warning and going on, or key keeping by the recoverer, for an action that does not come back. This wallet refuses, and other wallets may choose otherwise.
              • Plain coins at a vault address. Tokens there can be moved to an ordinary address. Bitcoin Cash there leaves only when everything is sent, or as the fee of a cancel.
              • Labels. The backup can hold them. The wallet sets none.
              • Closing for a user. It is a function that the test runs call, with no screen or tool of its own.
