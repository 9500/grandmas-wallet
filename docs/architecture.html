Grandma's Wallet architecture

A Bitcoin Cash wallet whose key can be replaced. This page explains how funds and application positions survive that replacement, what the wallet asks of applications, and where today's applications do not yet fit.

Prototype on chipnet State of 16 November 2026 Contracts not audited

The idea

An ordinary wallet is its key. Every coin and every application position names that key, or its hash. When the key is gone, nothing can stand in for it.

Grandma's Wallet puts a name between the two. Coins and positions name the wallet's identity, a token that never changes. The identity records which key may act for it today. That record can be rewritten: by the owner at any time, or by a trusted recoverer after a public waiting period that the owner can cancel.

What happens to your things when the phone is lost

Recovery replaces the key behind the identity. Nothing is moved, withdrawn or created again. The rest of this page follows from that one choice, including its costs: the wallet's coins sit in contracts, every spend carries the identity along, and applications must agree to name an identity where they name a key today.

Identity and controller

The identity is the category of one NFT, created in the wallet's first transaction. It is 32 bytes, for example a7b26de9…035935. The NFT lives in a single coin called the controller. Its commitment holds the wallet's state in 69 bytes that anyone can read from the chain.

The controller's script is built with the identity inside it, so each wallet has its own controller address and only that wallet's NFT can act there. Every step must keep the controller at input 0 and output 0, at the same script, with the same token and no less value. The script has four functions:

FunctionWho signsAllowed whenResult
ownerAuthorizeOwnerAlwaysController continues with the same owner and settings. A pending request is cancelled.
requestRecoveryRecovererNo request pendingPending, naming the hash of a new owner key. The waiting period starts with this output.
finalizeRecoveryRecovererPending, and the controller coin is older than the delayThe named key becomes the owner. The epoch goes up by one.
ownerUpdateOwnerAlwaysNew owner key, recoverer or delay. A pending request is cancelled. A new owner starts a new epoch.

Signatures must cover every input and output (signing type 0x41 or 0x61), so an approval cannot be moved to another transaction or have outputs swapped.

    Two things to notice while trying it. The recoverer can start a request at any moment, with no proof that anything was lost: the protection is the waiting period, during which a working wallet sees the request and cancels it. And the recoverer chooses the new key, so once nobody cancels, the recoverer is trusted to hand the wallet to the right person.

    Approving a spend

    Wallet funds and application positions are protected outputs. A protected output holds no key and checks no signature. It checks two facts about the transaction that spends it:

    1. Input 0 is the controller of its identity.
    2. Output 0 is that controller again, with the same owner, epoch, recoverer and delay, and no request pending.

    Only ownerAuthorize produces that successor, and it needs the owner's signature over the whole transaction. One signature on the controller therefore releases every protected input beside it. The presence of the controller alone proves nothing, because the recoverer spends it too.

    Who can spend what

      What this design costs

      • Every spend carries the controller: one extra input and one extra output, always at position 0. Eleven transactions of the scripted run cost 8,763 satoshis in fees.
      • One spend at a time. All approvals pass through a single coin, so two transactions cannot be prepared side by side; the second must build on the first.
      • Safety rests on the controller. A protected output trusts that no path to the unchanged successor exists without the owner's signature. A later controller version must keep that property; the state's version byte ties an application to the rules it was written against.
      • The wallet software must show everything being spent, since a single signature releases all of it.

      Inside the wallet

      The prototype is a web page. Everything that touches a key runs in the browser; servers hand out files and keep sealed records. The XO engine holds the keys and templates and builds and signs every transaction.

      Addresses

      The wallet has one receiving address: the asset contract built with its identity. It stays the same when the owner key is replaced, so an address given out years ago keeps working after recovery. It is a 32-byte script-hash address, and it holds BCH, fungible tokens and NFTs alike.

      The recovery credential is a separate mnemonic made for this purpose. It is unrelated to the owner's mnemonic. The wallet sets aside 4,666 satoshis for the recoverer's fees when it is created, enough for three requests and one completion.

      Templates

      An XO template is a JSON document that describes a contract system for a wallet engine: its roles, its actions, the transactions those actions build, the scripts, and the variables each needs, all with names and descriptions meant for people. A template is identified by a hash of its content.

      The wallet's own template

      Roles Owner and Recoverer. Five actions: Set up wallet, Approve, Change recovery settings, Request recovery, Complete recovery. This is the controller and the asset contract, described for the engine.

      An application's template

      Brought by the application, unknown to the wallet. The demo's Savings Jar has two actions, deposit and withdraw, one script bound to an identity and an unlock time, and no keys of its own.

      The wallet contains nothing about any application. A test fails if its code mentions the jar. Every application action is carried out the same way, by wrapping it in the wallet's own Approve:

      1. Trust. A template the wallet has not seen arrives with the request. The wallet shows its name, description and actions and asks the user to trust and remember it, or decline.
      2. Read. The engine builds the requested action on a throwaway invitation. The wallet reads off the result: which scripts are paid, how much, and the lock time.
      3. Wrap. The wallet builds Approve around that: controller first, the position being spent if any, wallet funds if needed, the template's outputs, the rest back to the wallet's address. The fee is set from the size as built.
      4. Record. Each output on which the wallet has a role becomes a position. Its record, with the template, action, role, output and variables, is written to the backup stores before anything is signed.
      5. Show and send. The user sees the template's words next to the wallet's own figures and approves. The transaction passes the wallet's own script check, then goes out.

      A position lists the actions its template offers the wallet's role. That is how a jar is emptied from the wallet page on a new device when the application is not there at all.

      Trusting a template is a real act of trust. The wallet shows its own figures beside the template's words, but nothing checks that the template's scripts do what its descriptions say. A review and distribution model for templates does not exist yet.

      Recovery

      Recovery needs two things that are prepared long before the phone is lost: a package in the recoverer's hands, and an archive that the wallet keeps current by itself.

      1. 1
        Owner, once

        Set up recovery

        The recoverer shows a link with its name and encryption key. The wallet seals a package to that key and hands it over as a link or QR code. The package holds the identity and creating transaction, the recovery credential, where the archive is and the key to read it, and the agreed settings. Someone who records the link learns nothing.

        The recoverer checks the package against the chain and leaves a signed note in the archive. Only then does the wallet show "Recovery is on".

      2. 2
        Wallet, every day

        Record before signing

        Before the wallet signs anything that creates a position, it writes a record to the backup stores and waits for them to confirm. If they do not, it does not sign. Records are signed with the owner key and encrypted with the archive key. The recoverer can read them and cannot forge them.

      3. 3
        The phone is lost

        Nothing happens on chain

        The chain cannot know. The owner contacts the recoverer by whatever means the two agreed on, and proves who they are in whatever way the recoverer asks.

      4. 4
        Recoverer and new device

        Request

        The new device makes its own key and shows it to the recoverer. The recoverer signs requestRecovery naming that key's hash. The recoverer never sees a private key of the owner, old or new.

      5. 5
        Everyone can watch

        Waiting period

        The request sits on chain for the agreed delay, counted in units of 512 seconds by the network's clock. A wallet that still works sees it, warns, and can cancel with one transaction, or cancels by itself if set to. A cancelled request has no effect.

      6. 6
        Recoverer

        Complete

        finalizeRecovery installs exactly the key named in the request and starts a new epoch. The old key stops working for everything bound to the identity.

      7. 7
        New device

        Take over and restore

        The device reads the controller's history from the chain, which gives the owner of every epoch. It fetches the records from the stores, keeps those signed by the owner of their epoch, rebuilds each position's script and requires it to equal the recorded one, then looks on chain. The result is either complete or a list of what could not be resolved.

        In the chipnet run the new device emptied a savings jar it had never seen, from the archived template alone, with the application not connected.

      Where the new device gets everything

      From the chain

      The controller's whole history and current state. Funds, at the address that follows from the identity. Whether each position's coin exists, was never made, or is spent.

      From the package

      Which wallet, its creating transaction, the recovery credential, the archive's location and key.

      From the archive

      Application templates in full, and one record per position: the action that made it, the variables, the script.

      What the recoverer can and cannot do

      Cannot
      • Spend, before or during the waiting period
      • Complete a request early or change the key it names
      • Attach a withdrawal to a request or a completion
      • Write a record the wallet would accept
      Can
      • Start a request at any time, without proof of loss
      • Hand the wallet to a key of its choosing if nobody cancels in time
      • Read the archive: what the wallet holds with applications
      • Cause cost and nuisance with repeated requests, until the owner replaces it

      Tokens, NFTs and application state

      Tokens in the wallet

      The asset contract holds BCH, fungible tokens or an NFT at the same address and puts no rule on outputs, so tokens move the way coins do: the owner approves, the wallet decides where they go. This is true of the contracts and their tests. The prototype's pages show and send BCH only, and the wallet refuses application actions that create tokens.

      An NFT held this way follows the identity. That matters for applications that say "whoever holds this NFT owns the position": such a position can change hands with the wallet, as long as the wallet can bring the NFT into the application's transaction. Whether it can is the question of composition below.

      Where an application keeps its state

      In script parameters

      Hidden behind a script hash until the coin is spent. The jar's unlock time; the terms of an AnyHedge contract. A new device can find the coin only with a record of the parameters.

      needs a record
      In an NFT commitment

      Readable on chain at any time. The controller's 69 bytes; a Moria or ParyonUSD loan. Found by anyone who knows which token to look for.

      on chain
      On a service's server

      Contract terms, counterparty data, history kept by the application's operator. Gone when the service is.

      out of reach

      Four conditions for a position to survive

      A position is recoverable only if all four hold. They are independent: perfect records cannot repair a fixed key, and a perfect contract cannot be found without its parameters.

      Authority

      The contract accepts whoever owns the identity now. A key or key hash inside the contract fails this.

      Information

      A new device can find the coin and rebuild its script, from the chain or from a record written before the position existed.

      Composition

      The owner's approval fits into the application's transaction: the controller at input and output 0, beside whatever the application requires.

      Connection

      The application can ask this wallet to act. A wallet with no keys to share cannot serve an application that builds transactions from them.

      What a position record holds

      Kind
      xo-template-output: an output of a template the wallet trusts
      Template
      Identifier and content hash; the full text is kept beside it, exactly as it arrived
      Origin
      The action, the wallet's role, and which output
      Parameters
      The action's variables
      Script
      The locking script, to compare against what the engine rebuilds
      Chain of custody
      Network, identity, number in sequence, the record before it, the signer's epoch; status prepared, confirmed or closed

      A record is a hint about where to look, never an instruction. It cannot make the wallet treat an address as its own unless the address follows from the identity by the template's rules.

          A bridge from the wallet's side: the pocket

          Three of the four already separate ownership from keys. What stops them is position and connection. The position problem could be met from the wallet's side, with no change to the applications' contracts, by a second kind of address called here a pocket.

          This is a proposal. It is not built and has not been reviewed.

          What a pocket is and where it lives

          A pocket is a contract address of the same wallet, next to its main address. It is not a second wallet, an account or a service: it exists only as coins on chain locked by one small script. The script is built from two values, the wallet's identity and the hash of a pocket key, and it can be opened in two ways:

          Way in 1: through the controller

          The owner's approval on the controller, exactly as for the main address. No signature of its own. This is the way a new device uses after recovery.

          Way in 2: the pocket key

          A signature of the pocket key. The controller is not in the transaction, so the coin fits whatever layout an application demands.

          contract Pocket(bytes32 identity, bytes20 pocketKeyHash) {
    function ownerSpend()                { ownerApproves(identity); }
    function keySpend(pubkey pk, sig s)  { require(hash160(pk) == pocketKeyHash);
                                           require(checkSig(s, pk)); }
}

          A sketch of the script, in the language of the project's other contracts.

          Only what an application needs would sit there: the NFTs that prove ownership of positions (a Moria borrower NFT, a ParyonUSD loan key or staking receipt) and a little BCH for those transactions. Savings stay at the main address.

          Who holds the pocket key

          Owner's device
          Holds the pocket's private key, derived from the owner mnemonic on a path of its own. It never leaves the device.
          Recoverer
          Does not hold it and does not need it. The package and the archive contain only the key's hash, which is public information. With it the recoverer can see what is in the pocket and cannot spend it.
          Backup stores
          Hold the sealed record with the hash. They can read nothing.
          New device
          Never learns the old pocket key. It reaches the old pocket through the controller, and makes a pocket key of its own.

          The record of a pocket, 20 bytes of key hash, is written to the backup stores before anything is sent there, like every other record. Without it a new device could not work out the pocket's address.

          The fourth row is the cost of the idea. Completing a recovery switches off the old owner key everywhere at once, because every coin asks the controller. The pocket key is checked by the pocket's own script, which cannot see the controller unless the controller is in the transaction, so it stays valid until the coins have left. A script cannot be given an expiry date either: the network can require "not before" a time and has no "not after".

          How the NFTs reach the new pocket

          The new device does this as its first transaction after taking over. Applications take no part in it.

          1. It reads the old pocket's record from the archive, works out the address from the identity and the old key hash, and finds the coins there.
          2. It makes its own pocket key and writes the record of the new pocket to the backup stores.
          3. It builds one transaction with the wallet's ordinary Approve: the controller first, signed by the new owner key, then every coin of the old pocket, each opened through the controller. Each NFT goes to the new pocket's address with its category, commitment and capability unchanged.

          A Moria loan names the hash of the borrower NFT's category and commitment. A ParyonUSD loan answers to an NFT of the loan's own category. Neither value changes when the NFT moves from one address to another.

          What a pocket does not solve

          • Someone still has to build the application's transaction around a pocket coin. Over WalletConnect an application asks the wallet for its address and leaves the wallet's inputs for the wallet to unlock, so a wallet could give its pocket address and unlock those inputs itself. That is untested; the application's fee would be set for a smaller input, and an application that takes a key hash out of the address would fail. Over WizardConnect an application derives addresses from the public keys the wallet shares and would never find a script address. It would need the wallet to name its addresses, or the wallet to build from a template.
          • Positions with a key inside. A Cauldron pool or an AnyHedge early exit made with the pocket key is as lost as with any other key.
          • A device found later. For the main address a completed recovery ends the old device's power. For the pocket it ends only when the contents have been moved, so that move must come first.
          • A thief gains nothing new before recovery completes, since the owner key on the same device spends everything without delay. The pocket is no weaker than the main address in that period, and no stronger.

          Limits and sources

          Limits of the prototype

          • The contracts have not been audited. Everything runs on chipnet.
          • Mnemonics are stored unencrypted in the browser.
          • The monitor watches only while the wallet page is open. A phone wallet needs background watching, which is not built.
          • The wallet refuses application actions that create tokens, and ones whose inputs need a waiting period of their own.
          • The wallet refuses templates with a variable of type timestamp: the engine reads such a value back differently when unlocking, and the coin could not be spent.
          • A position paid for entirely from outside the wallet leaves no trace in the controller's history, so an out-of-date archive would hide it.
          • The link that carries the archive key to the new device is not sealed. It gives a view of the records and no power to spend.
          • No screen yet for changing the recoverer or the backup stores.
          • The production length of the waiting period is an open decision. The demo uses one unit of 512 seconds.
