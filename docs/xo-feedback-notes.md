# XO developer feedback — raw notes

Factual observations collected during development. These are source material only: the bounty feedback itself must be written personally.

Format: date — what was tried — what happened — steps to reproduce if it is an issue.

## Observations

- 15 Nov 2026 — Reading the docs to plan key handling. The engine API docs say "Each secret holds a derivation index, not a key", and the engine exposes no method to import an externally generated key or secret. A role whose key is created by another party (here: a recovery key generated by the wallet owner for the recoverer) cannot be attached to an account directly.
- 15 Nov 2026 — `@xo-cash/state` documents `RemoteEncryptedStateManager` as "Not implemented yet", while the package overview mentions state sync with remote servers.
- 15 Nov 2026 — The getting-started page installs `@xo-cash/engine@0.1.0-next.17612568780`; the `next` dist-tag and the web dev wallet are on `0.1.1-next.18029697917`. The engine's own dependencies pin older versions of `state`, `types`, `utils` and `primitives` than those packages' `latest` tags.
- 15 Nov 2026 — The getting-started page names the parts of a template but gives no full schema; the multisig and wrapped-BCH templates in `@xo-cash/templates` were the practical reference for the format.
- 15 Nov 2026 — `xo-web-devtool` has no licence declared (no `license` field, no LICENSE file), so its code cannot be reused as a starting point for a wallet UI.
- 15 Nov 2026 — Opening an engine in Node with `storageType: StorageType.SQLITE` (engine 0.1.1-next.18029697917, state 0.0.5). `Engine.create` throws `TypeError: this[#storage].listScriptHashes is not a function`. The SQLite storage class only implements template methods (also in state 0.0.6). Reproduce: `Engine.create(mnemonic, { network: chipnet, storageType: StorageType.SQLITE, databasePath: './', databaseFilename: 'x' })`. Worked around with `import 'fake-indexeddb/auto'` and the default storage.
- 15 Nov 2026 — `engine.stop()` in Node rejects with `AggregateError: All promises were rejected` (empty `errors`), which ends the process with an uncaught exception unless caught.
- 15 Nov 2026 — On chipnet the engine logs "Failed to synchronize block headers … Header '00000000000ecc71…2671' at height 332451 claims target 486604799, expected 437753688" and then "Failed to process transaction update: Could not validate a block header on height N: The requested header is ahead of the current checkpoint" for every later confirmed transaction. `getChainStatus()` stays about 500 below the tip. Unspent outputs are still listed.
- 15 Nov 2026 — Token fields in a template output (`token.category`, `token.nft.commitment`) accept `$( … )` only when the whole field is one evaluation; a literal prefix followed by `$( … )` is treated as a literal and fails with "NFT commitment must be a valid hex string". Inside the evaluation, variables are inserted as text, so `<a> <b> OP_CAT` joins hex text, while `<0x0100> <bytesVar> OP_CAT` or `OP_HASH160` produce bytes that are then decoded as UTF-8 and rejected. Key operations such as `<ownerKey.public_key>` are not available in token fields ("Missing required variable: variableNames [ownerKey.public_key]"), so a commitment containing a key hash needs that hash passed as a separate variable.
- 15 Nov 2026 — A private key is derived under the template identifier. Editing a description in the template changes the identifier and therefore every key. This was only discoverable from a doc comment on `SecretData.templateIdentifier`.
- 15 Nov 2026 — Bundling the engine for a browser with Vite fails out of the box: `@xo-cash/state` imports `fs`, `path` and `better-sqlite3` at the top level. The web dev wallet's `vite.config.mts` shows the needed aliases and polyfills; this is not in the getting-started guide.
- 15 Nov 2026 — The getting-started guide and the engine README example use different, partly outdated API names (`setFallbackLockingParameters`, `getSpendableResources`, `listStartingActions` appear in the repository example but not in the published engine).
- 15 Nov 2026 — A locking script that is identical for all users (no per-user data in the script) is tracked by script hash, so an account sees every user's outputs at that script as its own, marked selectable.
- 15 Nov 2026 — Cause of the chipnet header failure above: `@electrum-cash/checkpoint` 0.7.2 has `asertIdealBlockTimeInSeconds: 600` for chipnet. Chipnet moved to one-minute blocks at height 332451 (12:35 UTC, 15 Nov 2026); that block claims minimum difficulty after a 160-second gap, and later blocks use roughly a tenth of the earlier difficulty. No newer `@electrum-cash/application`, `@electrum-cash/checkpoint` or `@xo-cash/engine` release existed on that date.
- 15 Nov 2026 — Signing with `<key.schnorr_signature.all_outputs_all_utxos>` in a transaction with two inputs produces signatures the network rejects ("mandatory-script-verify-flag-failed"). In `prepareInputUnlockingCompilation` the compilation context gets `sourceOutputs = []; sourceOutputs[inputIndex] = <this input's spent output>`, so the spent outputs of the other inputs are missing from the signing data. Checked by recomputing the signed message: the engine's signature verifies only when the other inputs' spent outputs are left out. `all_outputs` is unaffected. Reproduce: a template whose unlocking script uses `all_outputs_all_utxos`, an invitation with two inputs, `signInvitation` for each, `executeAction` with broadcast.
- 15 Nov 2026 — `executeAction(id, { broadcastTransaction: true })` threw `UnspentOutputNotFoundInStoreError` from `clearInvitationUnspentOutputReservations` after the transaction had been broadcast and accepted (the spent output had apparently already been removed from the store by the server notification). Seen once in three payments with the standard wallet template.
- 15 Nov 2026 — An input given only as an outpoint, for a locking script with several possible unlocking scripts, fails with `TemplateUnlockingScriptNotFoundError`; it needs `inputIdentifier` naming the template input. The getting-started guide does not mention `inputIdentifier`.
- 15 Nov 2026 — The key used to unlock an input comes from the invitation that first produced that input's locking script in this account's state, not from the invitation doing the spending, when both exist. In one process, a second invitation that generated the same secret identifier got derivation index 1, and the spend then mixed two different keys for the same identifier across its inputs.
- 15 Nov 2026 — The fee estimate is a fixed 160 satoshis per input and 120 per output; a 540-byte covenant input needs several times that, so `addChangeToInvitation` leaves too little fee for such transactions.
- 15 Nov 2026 — The key derivation path (`m/42415'/{template index}'/0'/{index}` on test networks, with the template index taken from the first four bytes of the template identifier) is documented only in source comments of `@xo-cash/crypto`.
- 15 Nov 2026 — What worked well: importing a template built on externally compiled bytecode; funding an action in one template from outputs of the standard wallet template in the same invitation; creating a CashToken identity (category from a spent outpoint) through an invitation; the engine in a browser keeping templates, keys and invitations across a reload.
- 15 Nov 2026 — With the signing fix applied locally, and separately with `all_outputs` on the unmodified engine, a complete multi-contract flow ran on chipnet: a covenant with an NFT state, a second covenant spent in the same transaction, a second account acting with its own key and paying fees from the standard wallet template, and an input with a relative-timelock sequence number set from a template expression.
- 15 Nov 2026 — The chipnet rule that header verification needs, read from Bitcoin Cash Node merge request !2184 (CHIP-2025-03 Faster Blocks) and confirmed against 324 chipnet headers with no mismatch: from height 332451 the ideal block time is 60 seconds; the ASERT anchor and half-life are unchanged; the target is computed from accumulated ticks (600 per block before, 60 after) and multiplied by 600/60; the test-network minimum-difficulty rule applies after a gap of more than 120 seconds. Details and the check are in `docs/xo-spike.md` and `spikes/xo-engine/16-chipnet-difficulty.ts`.
- 15 Nov 2026 — With the header fix applied locally, errors of the form "Could not validate a block header … ahead of the current checkpoint" still appear for transaction updates that arrive in the first seconds after `Engine.create`, before header verification has reached the tip (44 such errors when listing outputs immediately, none when waiting for `getChainStatus()` to show the tip first).
- 16 Nov 2026 — An invitation that is built but not sent keeps its inputs reserved. `listSpendableUnspentOutputs` then no longer offers them, and nothing says why: after one refused broadcast the account looked empty. `archiveInvitation` releases them. A started multi-party invitation holds its inputs the same way while the other party has it.
- 16 Nov 2026 — `executeAction` with `broadcastTransaction: true` reports a node's refusal as a string inside nested error messages, for example `...rejected by network rules.\n\nnon-BIP68-final (code 64)`. Telling "too early" from "invalid" means matching text.
- 16 Nov 2026 — The engine in a browser: works in a page with a strict content security policy if `wasm-unsafe-eval` is allowed and the two default chipnet servers are listed for connections. State is separate per mnemonic, but only one engine can be open in a page; the recoverer's page loads again to switch accounts.
- 16 Nov 2026 — The engine broadcasts through its own servers, so an application that reads the chain from another server can be asked about a transaction that server has not seen yet (16 Nov). Seen as a missing controller transition right after a broadcast.
- 16 Nov 2026 — A wallet that carries out actions of templates it has never seen needs to ask "what would this action do?". That works with what the engine has: `createInvitation` on the template, `appendInvitation` with the transaction's outputs, `buildInvitationTransactionFromMergedCommit`, then `archiveInvitation`. The unsigned transaction gives each output's script and amount, the lock time from a `locktime` expression, and the inputs' sequence numbers, with a made-up outpoint as input. A method that returns this without storing an invitation would be simpler and would not need the clean-up.
- 16 Nov 2026 — Appending an output to an invitation makes the account follow that output's script from then on, and it stays followed after the invitation is archived. Useful (it is how a device taking a wallet over starts following a position), but nothing in the documentation says so, and there is no direct way to follow a script of a template for given variables other than through the default policy, which covers one locking script per template.
- 16 Nov 2026 — An invitation belongs to one template. A transaction that needs inputs and outputs of two templates (a wallet's controller and an application's position) works when it is an invitation of one template with the other's outputs given as plain outpoints and raw outputs: inputs are unlocked by the script the account follows them under. The other template's transaction definition (its lock time, its outputs) is then not applied and has to be read out separately, as above.
- 16 Nov 2026 — A variable of type `timestamp` given as a number locks correctly and cannot be unlocked. The value is stored with the script hash as text (`1794847127`); `parseStoredVariableValue` turns stored text back into a number for `integer`, `bigint`, `satoshis` and `token_amount` only, and `convertInvitationVariableValueForCompiler` then takes the text for hex because it consists of hex digits. The unlocking script is compiled with five other bytes in place of the number, so the redeem script no longer hashes to the output's address; evaluating the transaction locally reports exactly that. Reproduce: a pay-to-script-hash locking script with `<when>` in it, `when` of type `timestamp`; pay to it, then spend it. With type `integer` the same template works. A wallet would like `timestamp`, to show the value as a date.
- 16 Nov 2026 — A template's identifier depends on the order of its fields: the same template with its keys sorted gets another identifier (`generateTemplateIdentifier` gave `1ab1d4f0…` and `5f2b6007…` for the two). Anything that stores a template as JSON and writes it back in another order, as a canonical encoding does, silently produces a different template, with different keys for templates that have any. Found when a device restoring a wallet could not find the template its records named.

- 17 Nov 2026 — Pointing the engine at a local regtest chain (Bitcoin Cash Node 29.2.0, Fulcrum 2.1.4) for fast tests. The engine knows `mainnet`, `chipnet` and `testnet4` only. It works with `network: chipnet` and a custom `electrumServers` entry, with three things found by trial: a listed server is contacted over `wss` only ("is missing 'wss' transport"), so the entry has to be a prepared `ElectrumWebSocket` with `encrypted: false`; the version must be at least 1.5.2; and a checkpoint at the genesis block fails ("Failed to request 'blockchain.block.header'", the server answers with plain hex for height 0), while a checkpoint at block 1 with the root from `blockchain.block.header(1, 1)` works. Header verification then reaches the tip without errors. Script: `spikes/xo-engine/regtest.mjs`.
- 17 Nov 2026 — `importTemplate` returns another identifier than `generateTemplateIdentifier(template)` gives for the same object. The engine's identifier is the hash of the template as its parser writes it out: `generateTemplateIdentifier(parseTemplate(JSON.stringify(template)))` equals it for all five templates tried; the direct call gave a different value for each (`spikes/xo-engine/28-template-identifiers.ts`). Keys worked out outside the engine from the direct value are at the wrong place in the key tree.
- 17 Nov 2026 — A second `Engine.create` in the same Node process fails with "Cannot configure storage for cache after it has been initialized", also after `stop()` on the first. Tests that need two accounts run one process for each.
- 17 Nov 2026 — What the engine hears about a transaction before its header check has reached the tip is dropped ("Could not validate a block header on height N: The requested header is ahead of the current checkpoint") and is not asked for again: after a restart against a chain of 1,400 blocks, a coin at a script made known right after `Engine.create` was never listed. Waiting until `getChainStatus()` shows `verifiedHeight >= currentHeight` before making scripts known avoids it.
- 17 Nov 2026 — Right after `executeAction` has sent a transaction, `listUnspentOutputs` can still list the output that transaction spent. Reading "the current controller output" straight after an action gave the old one; waiting for the output created by the transaction just sent is needed.
- 17 Nov 2026 — `listUnspentOutputs` entries carry `scriptHash` and no locking bytecode; tying an output to a locking script takes a second call, `listScriptHashes`.
- 17 Nov 2026 — A template's `defaults.address` with `generate` and caller-supplied variables gives one script per call, each with the next key and the caller's values, and the engine follows it. The values are kept with the script and used again at spending time, so one invitation can unlock several inputs of one script with a different value each. This made one address per coin possible without any change to the engine. Making 300 such addresses took 4.8 seconds.
- 17 Nov 2026 — Key numbers are handed out per template, in order, across all key variables of the template. Two kinds of key that must not be children of one node therefore need two templates, and a device that restores has to make its addresses again from number 0 upward; there is no way to make number 57 known alone.
- 17 Nov 2026 — What worked well: a whole wallet's life through the unmodified engine on a local node with five templates (a controller with two roles, two templates of one-key-per-address scripts, a template of scripts without keys, and the standard wallet template): creation of a token identity, a payment with change, a request and a completion by a second account with a relative time lock, a cancellation, a new seed taking over an identity it never saw created, a sweep with inputs of three templates, and a closing that destroys the identity token. Every transaction had exactly the size worked out beforehand from the kinds of its inputs and outputs (`spikes/xo-engine/27-wallet-templates.ts`).
- 17 Nov 2026 — An action that makes a key has to be carried out in the invitation the key was made for. Reading the controller key from one invitation (start intent with `generate`) and then creating the wallet through a second `createInvitation` with the same start intent made a second key, number 1. The controller output was then followed under the second invitation, and the engine later unlocked it with key 1 while the state named the hash of key 0. The network would have refused the transaction; this project's own check before sending caught it. Appending the inputs, variables and outputs to the first invitation instead works.
- 17 Nov 2026 — `generateLockingBytecodeFromDefaultPolicy('receive')` on the standard wallet template gives a new address at every call. An account that wants one stable address for ordinary coins has to keep the first one itself.
- 17 Nov 2026 — A template's `supported` list is part of its content and so of its identifier, and the type lists network versions up to `BCH_2026_05`. A template whose keys must never change cannot name next year's version today. Whether the engine will go on running a template that does not list the then current version is a question for XO.
- 17 Nov 2026 — An invitation whose transaction the network refuses (here: a completion sent before its relative time lock had passed) keeps its inputs reserved. The next invitation that names the same outputs fails with `UnspentOutputReservationExternalConflictError`. Archiving the refused invitation releases them; the driver now does that whenever a broadcast is refused.
- 17 Nov 2026 — With three chipnet servers given to the engine (one of our own and the two it names), the process ended while waiting for a block: `Error: No block headers were returned when requesting 1 headers from height 335851`, thrown in `requestBlockHeadersBatch` of `@electrum-cash/application` and not caught anywhere. The function asks every server for the new block's header and takes the first answer (`Promise.any`); a server that has not seen the block yet answers at once with an empty list, and that answer wins. With one server it did not happen in the rest of the run.
- 17 Nov 2026 — What worked well: the same whole life of a wallet on chipnet through the engine (with the local header fix and one server), nine transactions by three accounts, each in a process of its own with an empty state: creation, a payment, a request and a completion after a 512-second relative time lock, a sweep of six coins of three script kinds with an NFT in one transaction of 2,437 bytes, a payment, the NFT sent on, closing. Every fee was exactly the size at 1 sat/byte (`docs/runs/stage-5-chipnet.md`).
- 18 Nov 2026 — The engine in two web pages built on it (a wallet and a recoverer), in Chromium with a strict content security policy, against a local regtest chain: creating a token identity, paying, a cancellation, a change of the controller's settings, a sweep with inputs of three templates, a request and a completion were all built, signed and sent from the browser, by five browser profiles in one scripted course (`docs/runs/stage-6-local-node.md`). Opening an account takes one to two seconds there, most of it the header check.
- 18 Nov 2026 — When blocks follow each other within a second or two, the engine in a browser logs "Could not validate a block header on height N: The requested header is ahead of the current checkpoint at height N−1" to the console. Nothing visible followed from it in these runs; the coins and transactions were all there afterwards.
- 18 Nov 2026 — A page that looks after several accounts (a recoverer with one credential per wallet) has to load again to change account, because only one engine can be open. What such a page shows for all its wallets at once (where each controller stands, what each fee address holds) therefore cannot come from the engine and is read from an Electrum server directly.
- 18 Nov 2026 — The same two pages on chipnet, served publicly, with the local header fix built in: a wallet created, a request refused, a recovery after a 512-second waiting period, a sweep, a move to a new seed, a new recoverer and a restore, by six browser profiles (`docs/runs/stage-6-chipnet.md`). Opening an account in the browser takes about eight seconds there, most of it the header check from the checkpoint.
- 18 Nov 2026 — Each open page holds a connection of the engine to its server, besides the application's own. With five profiles open against one Electrum server behind a proxy, the server's limit of connections per address was reached, and the engine of the next page failed with "Cannot bootstrap the header accumulator: no electrum clients are connected". The engine does not try another server by itself when given one; the page now gives it the first of its configured servers that answers.
- 18 Nov 2026 — What worked well: a template the wallet had never seen, carried out through the unmodified engine with the wallet's own coins and addresses, on the first try. An invitation of the application's template took a coin held under one of the wallet's templates as its input (unlocked by that template's script), created a token category from that coin's outpoint, paid a script of the application's template and sent an NFT to an address of the wallet given through a `locking_script` variable (`"lockingScript": "$(<holder>)"`). A second invitation spent the application's coin (a script with no key, unlocked by `<keyInput>`) together with the NFT. Both transactions had exactly the outputs, sizes and unlocking bytes that this project's own reading of the template had worked out beforehand (`spikes/xo-engine/32-application-template.ts`, `docs/runs/stage-7-local-node.md`).
- 18 Nov 2026 — A token commitment written as `$(<n>)` with `n` of type `integer` does not give the number's bytes: the evaluation's result is decoded as UTF-8 text and then read as hex, and fails ("NFT commitment must be a valid hex string") or gives other bytes. A value given as hex text to a `bytes` variable works. A template that needs the same number in a script (as a number), in a lock time (`$(<n>)`, decoded as a number there) and in a commitment therefore carries it twice, as `integer` and as `bytes`, and nothing in the template ties the two together. An evaluation mode that gives hex for a token field, or `$(<n>)` giving the script-number bytes there, would remove the second variable.
- 18 Nov 2026 — To have the engine follow a script of a template for given values, an output with that script has to be appended to an invitation (which can then be archived). A script that no action of the template pays to in the account's role cannot be followed at all, and so a coin there cannot be unlocked by the engine. A call "follow this locking script of this template with these values" would serve a wallet that finds positions on chain by itself.
- 18 Nov 2026 — Every output that an invitation appends by its template identifier is followed afterwards, also one that is only a marker for someone else to find (`selectable: false`, no balance for the role). It then appears in `listUnspentOutputs` beside the account's own coins; a wallet that lists "its tokens" has to filter by template.
- 18 Nov 2026 — The validator rejects unknown properties at every level, so an output cannot say "the wallet locks this" (`"lockingScript": { "wallet": "receive" }`) and a template cannot carry a recovery declaration. Both travel beside the template for now: a `locking_script` variable that the wallet fills, and a companion document that names the template by identifier and by the hash of its text.
- 18 Nov 2026 — An invitation's inputs and outputs that a template gives an index (`inputIndex`, `outputIndex`) are placed first, in index order, and the others after them (`orderByTransactionIndex`). A template that leaves a place free for the other party's own item (here: ParyonUSD's key factory is input 1 because the coin that defines a new token category must be input 0; the factory's output 0 is the wallet's own plain coin) is therefore built in another order than intended: the engine put the factory at input 0. Giving every commit input and output its `transactionIndex` explicitly makes the engine build exactly the order asked for. Reproduce: a template transaction with `inputs: [{ input: 'x', inputIndex: 1 }]`, and an invitation with an outpoint input without index added before it.
- 18 Nov 2026 — What worked well: ParyonUSD's five borrower transactions (make a loan key, move a Borrowing thread to the current period with a lock time from a variable, borrow, manage, close), each an invitation of one template of this project's that carries Paryon's eight published contracts as literal redeem bytecode, built by the unmodified engine with the wallet's coins of two other templates at recoverable addresses (`spikes/xo-engine/33-paryon-template.ts`, on the local node with Paryon's contracts deployed there). Every transaction was byte-identical, outside the wallet's own signatures, to what this project's plain builders make for the same choices, and the node took each. The template uses `$(<a> <b> OP_SUB)` for a token amount, constants as locking scripts of outputs (`$(<burnLockingBytecode>)` for `OP_RETURN` outputs that carry tokens, `$(<protocolFeeLockingBytecode>)`), empty commitments, unlocking scripts that are only a comment (a contract function without arguments), and inputs at four shared contracts whose tokens the transaction partly burns without an output.
- 18 Nov 2026 — For the engine to unlock a coin of an application's contract it has to follow the contract's script, which it does only after an output with that script was appended to an invitation. A contract every user shares (Paryon's Loan script holds about 830 outputs on chipnet, its LoanKeyOriginProof script about 1,240) is then followed whole: every output of every user is fetched into the account's store and kept up to date on every change at that script, though the account needs one of them for one transaction. A way to name an input by outpoint, with its locking script and unlocking data from the template, without following the script, would serve an application whose contracts are shared.
- 18 Nov 2026 — A token field is evaluated as UTF-8 text (`$( … )` in `token.nft.commitment`), so a commitment that is a fixed-width record with one field changed (a loan's state with its debt less a repayment) cannot be worked out in the template: a number cannot be turned into hex text in CashAssembly without a long expression per byte. The page has to compute the whole commitment and pass it as a `bytes` variable. An evaluation mode that gives the bytes of the result as hex for token fields, as the `hex` decode mode of `compileCashAssemblyString` already does, would let a template write `$(<0x01> <newDebt> <6> OP_NUM2BIN OP_CAT …)`.
- 18 Nov 2026 — The engine checks no input of an invitation it builds in the virtual machine unless another participant's signatures are in it (`hasInputResolutions`); when it does check, it evaluates with only the input's own spent output, so a contract that reads other inputs (Paryon's all do) could not be evaluated there anyway. An application's transaction is therefore checked by the wallet itself, every input against every spent output, before the signature is used.
- 18 Nov 2026 — A template's `relevant: false` (on a locking script's role or an output's role) is read only when the invitation's output carries a `roleIdentifier`: `isLockingOutputRelevantForRole` answers "relevant" when the role is absent. An output appended as `{ outputIdentifier }` alone is therefore tracked even when the template says it need not be. With Paryon's Loan and sidecar scripts (about 830 and 280 coins on chipnet) this filled the account's store and stalled the process; adding `roleIdentifier` to each appended output made the engine leave those scripts alone.
- 18 Nov 2026 — An input given in a commit with its `unlockingBytecode` and `sequenceNumber`, at an outpoint the account does not track, is taken as another participant's input: the engine does not sign it, puts it into the transaction as given, and builds and signs the rest. This is how a wallet can spend a coin of a contract every user shares without following its script; the unlocking (arguments and redeem script, no signature) is compiled from the template by the wallet.
- 18 Nov 2026 — Following a script makes the engine's Electrum layer (`@electrum-cash/application`) process every transaction of the script's history: it fetches each, asks for its proof and stores both. A contract every user of an application shares has a long history (on chipnet Paryon's Borrowing script has 76,637 transactions, its price contract 17,358, its Loan script 48,595), and following one of them kept a Node process at full load for over ten minutes, the store growing past a gigabyte, until it was stopped. A wallet that spends one coin of such a contract wants neither its other coins nor its history.
- 18 Nov 2026 — In the stage 9 browser course on chipnet (pages built with the local fix for chipnet's block timing), the recoverer page's engine logged `Server reported merkle root … for checkpoint #336437, expected …` and then `Could not validate a block header on height 336441: The requested header is ahead of the current checkpoint at height 336437` for every transaction update, from the waiting period on. The recoverer still completed the move (its controller transactions are this project's own code), but its page did not get past "Opening this wallet's account. The page checks the chain's block headers first." for the rest of the run. The same message in the stored checkpoint after what looks like a chain reorganization of a few blocks suggests that the engine keeps a checkpoint it has stored and does not go back to an earlier one when the server's chain differs; it may need to drop and re-derive checkpoints above a reorganized height.
- 18 Nov 2026 — The same again in the wallet course on chipnet with this checkout's pages, and now confirmed as a reorganization: the chipnet node lists block `00000000e7e4bd8a…` at height 336473 as a `valid-fork` of one block, and the recoverer page's engine reported `Server reported merkle root 2dc43716… for checkpoint #336473, expected 49a7c6a8…` and `The requested header is ahead of the current checkpoint at height 336473` from then on; after a reload the page said "The engine's header check stands at 336473 of 336483". The node lists such one-block forks every few dozen blocks on chipnet. Deleting the engine's IndexedDB store `Electrum-chipnet-…` (headers, proofs, histories; the `XO` store with the keys untouched) and opening the page again brought it back within seconds, and the recoverer sent its fee coins. The pages now do this themselves, once in a row, when the header check has not moved at all for the two minutes an account waits for it (`packages/ui/src/engine-headers.ts`). The engine itself should roll its checkpoint back below a reorganized height.
- 19 Nov 2026 — Engine `0.1.1-next.18170561234` was published. Its own code is the same as `0.1.1-next.18029697917`, byte for byte; it depends on `@electrum-cash/application` `0.5.3-development.18109001223` and `@electrum-cash/checkpoint` `0.8.0`, which know chipnet's one-minute blocks. Unchanged, on chipnet, its header check reached the tip in ten seconds. The local fix is no longer applied. The signing of `all_outputs_all_utxos` is as before.
- 19 Nov 2026 — With engine `0.1.1-next.18170561234`, custom chain parameters given to `Engine.create` (a local regtest chain) need `asertIdealBlockTimeSchedule: [{ fromHeight: 0, idealBlockTimeInSeconds: 600 }]` in place of `asertIdealBlockTimeInSeconds: 600`. With the earlier field the header check fails with `TypeError: Cannot read properties of undefined (reading '0')` in `calculateAsertTarget` and stays at height 1. The engine's version number did not change in a way that says so.
- 19 Nov 2026 — With the same release, an output of a transaction the account just sent with `executeAction(..., { broadcastTransaction: true })` is listed by `listUnspentOutputs` about a second later (measured at about 1.0 s on a local node, polling every 0.5 s). With the release before, code that spent such an output immediately afterwards found it in three scripted runs, on the local node and on chipnet.
- 19 Nov 2026 — `getInvitation(id)` after `executeAction` returns the invitation with its `result.transactions` filled in (transaction hash, who created and who broadcast it); `serializeInvitation` from `@xo-cash/utils` gives a text of 3 to 11 kB that `deserializeInvitation` reads back. The stored record keeps the account's secrets apart from the invitation, so the text holds no key.
- 20 Nov 2026 — What worked well: an account on a new seed, with no history, followed and emptied a position another seed had opened, through the unmodified engine. It was given the template's text, the locking script's identifier, the role and the script's two values, appended an output with that script to an invitation of the template and put the invitation aside; the engine then listed the coins at the script and unlocked them (`docs/stage-11-trial.md` on the branch `design-3`). The first seed's `ScriptHashData` for the script held every value of the action that made it, not only the values the script uses.
- 20 Nov 2026 — The fields of `ScriptHashData` (template, locking script, role, variables) are what a wallet needs to carry from one device to the next to follow a script again. This project now keeps a record with those fields in its own sealed backup for each position, written before the action is signed, because `RemoteEncryptedStateManager` is not implemented and a synchronisation whose key comes from the seed could not be read after the seed is replaced.
- 20 Nov 2026 — A wallet that replaces its seed meets three things in XO as it is: keys made under an application's template are gone with the seed, the engine's state belongs to the earlier account, and nothing ties the new account to the earlier one's scripts. Scripts that take no key of the device (a token as the authority, as in the two applications tried) come back from the record; a script that takes a key of the device does not, and the wallet can tell which is which from the template alone, by whether a locking script the action pays uses a key variable.
- 20 Nov 2026 — The template schema has `importDefaultValue` on a variable; the engine as published never reads it. A variable's `hint` is accepted by the validator in any shape.
- 20 Nov 2026 — `executeAction` with `broadcastTransaction: true` stores nothing about the outputs of the transaction it sends. The account lists them only after its server reports the transaction and the engine reads its coins again (about a second on a local node), and the engine signs only coins in its store. A wallet that carries out two actions in a row has to note the first one's outputs itself and wait until the engine lists them. An `executeAction` that stores its own outputs, or a public call that takes a transaction in or reads the coins again, would remove the wait. (See also the note of 19 November.)
- 20 Nov 2026 — What worked well: two applications used from their XO template alone, with no companion document for the wallet, through the unmodified engine on a local node: a savings contract whose key NFT the template names as an input of its own, and ParyonUSD's public contracts with the template of 18 November unchanged. What the template does not say came from the application's page in the request (which coins of the application's, by outpoint; the values read from them; which token the action is about) and from the wallet's own record (`docs/runs/stage-17-jar-local-node.md`, `docs/runs/stage-17-loan-local-node.md` on the branch `design-3`).
- 20 Nov 2026 — A template cannot say what a wallet needs to act on a shared contract by itself: which coin at a script many users share belongs to this user, and the values in that coin's token. For ParyonUSD the page finds the loan from its key and reads the price coin; without the page the wallet can only say that the action is done through the application.
- 20 Nov 2026 — Asked about a call that makes the engine follow a script from a template, a locking script, a role and values, one of XO's authors answered that an action today results in a transaction or in data, and that XO expects to let an action result in a locking bytecode, with the invitation followed to its end. That would be the supported form of the invitation this project puts aside.
- 21 Nov 2026 — The schema lets a template give `relevant` as an expression, and the engine does not evaluate one yet. A wallet that has to know before signing whether an output will be its own to follow cannot tell for such a template: in which scope the expression is evaluated (the action's variables, the role, the invitation's participants) and what result counts as "follow it" are not stated anywhere. This wallet refuses such an action for now. A sentence in the documentation on how the rule will be evaluated would let a wallet work it out with the action's values before the engine does.
- 22 Nov 2026 — What worked well: an application's server took part in a wallet's invitation as a second participant, in a role of its own, through the unmodified engine. The wallet started the invitation, the server appended one commit with its values, its shared coins and their unlocking, and the wallet built, checked and signed the transaction. The ParyonUSD loan ran this way through its actions and through a recovery on a local node, with the loan page closed (`docs/xo-service.md`).
- 22 Nov 2026 — `acceptInvitation` checks neither the signatures nor the history of the commits it receives; `updateInvitation` does. A party that joins an invitation another party started calls `validateInvitation` itself. A commit's `expiresAtTimestamp` is not enforced by the engine and is not covered by the commit's signature.
- 22 Nov 2026 — When two commits state the same variable, the later one is used, and a role tag on a variable overrides the template's assignment of that variable to a role. A wallet that has another party join its invitation checks that the other party stated no variable of the wallet's role.
- 22 Nov 2026 — A template's `resources` entries take `name`, `description`, `icon` and `url` and nothing else; `url` is checked only as a string. This project names an application's service there by the exact name `xo_service_v1`.
- 22 Nov 2026 — `omitChangeAmounts` on a template input is in the schema, and the engine as published does not read it. A wallet that works out the change itself follows what the schema says it means: the coin's satoshis go toward the outputs and the fee, and what is left of them to the fee.
- 22 Nov 2026 — An output added to an invitation with a `roleIdentifier` that the output's locking script does not name is refused (`TemplateLockingScriptRoleNotFoundError`). Templates published at XO Grid have this shape where one role pays into a contract and another spends it: the script names only the spending role. This wallet now gives such an output without a role, with the locking bytecode it worked out.
- 22 Nov 2026 — The engine learns of a script from an output added in a role. A coin at a script that no action of the acting role pays to cannot be followed in that role; the wallet gives such a coin with its unlocking. `listOwnInputIndexes` still lists an input at a followed script whose unlocking was given, and signing it is refused (`InvitationItemFieldConflictError`), so the wallet leaves those inputs out when it asks for signatures.
- 22 Nov 2026 — On chipnet, an output to a contract address that many transactions share (about 44,800 transactions and 516 coins) made the engine follow that address; the server dropped the connection on `listunspent` and the process ended after the transaction had been sent. Given with its locking bytecode, the output is not followed, and the same run completed (`docs/runs/xo-grid-templates-chipnet.md`).
