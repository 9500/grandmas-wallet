Grandma's Wallet, clean-slate design

A Bitcoin Cash wallet whose key can be replaced by a trusted recoverer after a public waiting period. In this design the key is the everyday path and the controller is the recovery path only. Applications give authority to a token in the wallet, so recovering an application position is the same as moving a coin.

Design proposal 17 November 2026 Controller and vault are built; the rest is not
Identity and controller Owner and wallet coins Recoverer Application

Each part is marked built when it exists and ran on chipnet, proposed when it is designed here and not written, and open when it depends on something not yet checked.

The proposal

Every address of the wallet can be spent in two ways. The owner's key spends it directly, like any single-key wallet. The wallet's controller can also release it, and the controller obeys whoever owns the wallet's identity today. Recovery changes the owner of the identity. The new owner then moves every coin and token to an address of the new key.

Two ways into every coin

The four parts

1 · Wallet

Controller. One coin holding the identity NFT. Its state names the owner key, the recoverer key and the waiting period. Unchanged from the current build.

2 · Wallet

Recoverable address. A script with a key path for every day and a controller path for recovery. A second address kind, the vault, has the controller path only and never changes.

3 · Applications

Three rules. Authority is a token. The wallet's inputs and outputs are the wallet's business. The template says what a token means.

4 · Connection

The wallet builds the transaction from the application's XO template, over a WizardConnect session with the xo_v1 extension.

Why this and not the current build

The current build puts the controller into every transaction. That made each application carry the wallet's identity, fixed the controller at input 0 of every application transaction, allowed one action at a time, and made all of the wallet's activity visible at one coin. Three of the four applications we studied could not fit. In this design an everyday transaction is an ordinary one, and the controller appears only when the wallet is set up, recovered or swept.

Identity and controller built

The wallet's identity is the token category of one NFT. The coin that holds this NFT is the controller. The NFT's commitment is the controller's state, 69 bytes that anyone can read on chain. The controller's script accepts four actions and always sends the NFT back to itself with the next state.

ActionSigned byWhat it doesUsed in this design for
ownerAuthorizeOwner keyContinues the controller unchanged as Active. Cancels a pending request.Sweeps, spending from the vault, cancelling a request
requestRecoveryRecoverer keyMarks the state Pending and names the proposed new owner key. The waiting period starts.The first step of recovery
finalizeRecoveryRecoverer keyOnly after the waiting period. Installs exactly the proposed key and raises the epoch by one.The second step of recovery
ownerUpdateOwner keyReplaces the owner key, the recoverer or the waiting period.Moving to a new key without the recoverer, changing recoverer

Two properties carry the whole scheme:

  • The waiting period is enforced by the network. It is a relative time lock on the controller's own coin. Nobody can shorten it.
  • The recoverer never gains spending power. Coins released through the controller require it to continue unchanged, with the same owner and no request pending. A request leaves a claim pending and a completion changes the owner, so neither can carry coins with it.

The controller's script, its 69-byte state and the approval check used by coins (ownerApproves) stay exactly as built. What changes is how often the controller is used. The simulator under A wallet's life shows the state byte by byte.

The recoverable address proposed

This is the wallet's ordinary address. It is a script address (P2SH32) with two ways to spend. In our earlier discussion it was called the pocket.

contract RecoverableAddress(bytes32 identity, bytes20 keyHash) {
    // Everyday path: the key this address was made for.
    function spend(pubkey pk, sig s) {
        require(hash160(pk) == keyHash);
        require(checkSig(s, pk));
    }
    // Recovery path: whoever owns the identity today, through the controller.
    function sweep() {
        ownerApproves(identity);
    }
}
Spending address

The script above. One address per owner key in version 1. Used for everything the wallet does with applications. It changes when the owner key changes.

Vault address built

The existing Asset(identity) script: controller path only. It never changes, so it suits a published receiving address or a payout that arrives long after it was agreed. Spending from it needs the controller at input 0.

A new device that knows only the identity can therefore list every coin and token the wallet has ever been able to hold. No backup file is needed for that.

      Recovery flow

      The first three steps are as built. Step 4 is new. Step 5 is where applications come back.

      1. 1

        Request built

        Recoverer, with the new device

        The new device makes a key and gives its hash to the recoverer. The recoverer signs requestRecovery naming that key. The controller is now Pending, on chain, for anyone to see.

      2. 2

        Wait, and the owner's chance to refuse built

        Owner, if the phone is not lost

        The wallet watches its controller. If a request appears that the owner did not ask for, the owner cancels it with one signature. In this design paying someone no longer cancels a request by the way, because payments do not touch the controller. The cancel is its own action, by hand or automatic.

      3. 3

        Complete built

        Recoverer

        After the waiting period the recoverer signs finalizeRecovery. The proposed key becomes the owner and the epoch goes up. No coin has moved.

      4. 4

        Sweep proposed

        New device

        The new device reads the controller's history, works out every earlier address and lists what is there. It moves all of it to the address of its own key in transactions that carry the controller, signed by the new key with ownerAuthorize. Coins, fungible tokens and NFTs move the same way. The fee comes out of the swept coins.

      5. 5

        Understand what the tokens are proposed

        New device, with the applications' templates

        A swept NFT is already under the new owner's control. To show it as "a jar with 0.3 BCH that opens in March" the wallet needs the application's template, from its backup or from the application when the user connects again. Recovery does not wait for this.

      What each party needs

      PartyHoldsCan doCannot do
      Owner's deviceThe owner key; the identitySpend, cancel a request, change the recoverer
      RecovererThe recoverer key; the identityRequest and complete a recovery. See the wallet's coins, which are public in version 1.Spend anything. Shorten the wait. Complete with a key other than the one requested.
      New deviceIts own new key; the identity, told by the recovererAfter completion: sweep and spendAnything before the wait is over
      Backup storesSealed records: trusted templates, labelsHand the records backRead them. They are no longer needed to find coins or positions.

      What the waiting period does and does not protect. It protects against a recoverer who acts without being asked, as long as the owner notices in time. A recoverer who names their own key and is not cancelled gets the wallet. It does not protect against a thief who can use the owner's phone: such a thief can spend at once, in this design as in any wallet.

      Rules for applications proposed

      An application that follows these three rules is recoverable by this wallet, and by any other wallet that implements the same scheme, without knowing that recovery exists.

      Rule 1

      Authority is a token

      Whoever may act on a position is whoever spends its ownership NFT in the same transaction. Payouts go to an address the wallet supplied.

      No user key or key hash inside an application contract. A key cannot be replaced; a token can be moved.

      Rule 2

      The wallet's parts are the wallet's business

      The application does not assume the wallet's inputs are P2PKH or have a fixed size. Tokens and change go to an address the wallet names.

      "Back to the address it came from" is fine: after a sweep that is the new address.

      Rule 3

      The token leads to the position

      From the NFT alone (its category and commitment) and the template, a wallet can find the position on chain and list the actions it offers.

      No application server and no private note is needed to find a position again.

      Why these are enough

      • Recovery never touches an application contract. The sweep moves the NFT from one wallet address to another. The position stays where it is.
      • The application's transaction layout is untouched. The controller is not in application transactions, so fixed input positions do not collide with it.
      • A wallet can recover what it does not understand. An NFT of an unknown application is swept like any coin. Its meaning can be learned later.
      • The rules are checkable. Each can be tested against a contract's source and a template, so a conformance checker is possible.

      What the rules exclude: positions opened by a key written into the contract, positions whose owner is known only to a server, and front ends that insist on building the transaction themselves from the wallet's public keys.

      Template extension open

      An XO template already describes an application's roles, actions, transactions, inputs, outputs and scripts. The engine builds every transaction from it. Two things are missing for recovery: a way to say that an output is locked by whatever address the wallet chooses, and a way to say what a token means. The fragments below are sketches. The field names are proposals and have not been checked against the XO schema or discussed with its authors.

      1. An output the wallet locks

      "outputs": {
  "jarKeyOutput": {
    "name": "Jar key",
    "description": "The token that opens this jar. Keep it in the wallet.",
    "lockingScript": { "wallet": "receive" },        // proposed: the wallet's own address
    "valueSatoshis": 1000,
    "token": { "category": "$(<keyCategory>)",
               "nft": { "capability": "none", "commitment": "$(<unlockTime>)" } }
  }
}

      Today a template names a locking script for every output. Here the template leaves it to the wallet. The same marker on an input says "any coin of the wallet", with no assumption about its script.

      2. What a token means

      "recovery": {
  "profile": "recoverable-app-v1",
  "authority": {
    "jarKey": {
      "token": "jarKeyOutput",                       // which output creates the token
      "position": {                                  // how to find what it controls
        "lockingScript": "savingsJarLockingScript",
        "variables": { "keyCategory": "token.category",
                       "unlockTime":  "token.commitment" }
      },
      "actions": ["deposit", "withdraw"]             // what its holder can do
    }
  }
}

      A wallet that holds an NFT and trusts this template fills the two variables from the NFT, builds the jar's address, looks it up on chain and offers the listed actions.

      3. A position found through a companion coin

      "recovery": {
  "profile": "recoverable-app-v1",
  "authority": {
    "loanKey": {
      "token": "loanKeyOutput",
      "position": {
        "companion": { "lockingScript": "loanSidecarLockingScript",
                       "tokenCategory": "token.category" },
        "relative": -1                               // the loan is the output before its sidecar
      },
      "actions": ["manage", "close"]
    }
  }
}

      ParyonUSD keeps a small sidecar coin next to each loan, carrying the loan key's category. The wallet finds the unspent sidecar with that category; the loan is the output before it in the same transaction. This reading comes from the borrowing and manage contracts and has not been run.

      4. The wallet's own template

      The wallet's template gains the recoverable address as a locking script with two unlocking scripts, spend and sweep, and a sweep action whose first input and output are the controller. The existing approve action remains for the vault.

      How a wallet ties a token to a template without a backup. The backup keeps one line per token saying which template made it. If the backup is gone, the wallet can test a token against a template the user trusts: rebuild the position's address from the token and look for that address in the transaction that created the token. Proposed, not built.

      Talking to applications

      WizardConnect gives an application and a wallet an encrypted channel, started from an address the application shows as text or a QR code. What travels over it depends on what the wallet offers when it connects.

      Who builds the transaction

      The ordinary flow cannot serve this wallet. It hands the application the wallet's public keys, and the application derives P2PKH addresses from them and builds the transaction itself. This wallet's address is a script. We checked the live front ends of Moria and ParyonUSD on 16 November 2026: both refuse any wallet address that is not P2PKH, over WalletConnect as well.

      The xo_v1 extension version 2 built version 3 proposed

      A wallet announces the extension in the session. Nothing in it names an application.

      { "xo_v1": { "version": 3, "network": "chipnet",
    "profiles":  ["recoverable-app-v1"],           // proposed: the rules this wallet relies on
    "bindings":  ["receive", "change"],            // values the wallet fills in itself
    "templates": [{ "identifier": "…", "contentHash": "…" }] } }
      MessageDirectionMeaning
      xo_action_requestapplication → walletThe template (or its identifier if the wallet has it), the action, the role, the variables, and which of the wallet's tokens the action spends
      xo_action_responsewallet → applicationTaken on, or refused with a reason
      xo_invitation_updatewallet → applicationApproved by the user, recorded in the backup, sent
      xo_action_resultwallet → applicationThe transaction and the tokens the wallet received, or an error
      xo_positions_request / xo_positionsbothWhich tokens of this template does the wallet hold? Answered only for a template the user trusts.

      What changes from version 2

      • No identity binding. Version 2 let the application ask the wallet to fill its identity into the application's script. Applications no longer see the identity at all.
      • A position is a token. The wallet reports the NFTs it holds under a template, read from the chain, where version 2 reported records from its backup.
      • The wallet signs with the address key. Version 2 wrapped every action in the wallet's approve action around the controller. That wrapping goes away for application actions.

      The rules the wallet follows stay: an unknown template is shown to the user and trusted only on their word; a request is carried out at most once per id; the user sees the template's wording next to the wallet's own figures from the built transaction.

      This is the part that most needs XO. XO has invitations and a sync client but no protocol between a website and a wallet. xo_v1 is our own. A standard would best come from XO, or as a WizardConnect extension both projects agree on.

      The new Savings Jar proposed

      A jar holds savings until a date. Today there are two jar contracts: one bound to the wallet's identity for Grandma's Wallet and one bound to a key for ordinary wallets. In this design there is one, and it knows neither.

      contract SavingsJar(bytes32 keyCategory, int unlockTime) {
    // Deposits are ordinary payments to the jar's address.
    function withdraw(int keyInput) {
        // Opens for whoever spends the jar's key NFT in this transaction.
        require(tx.inputs[keyInput].tokenCategory == keyCategory);
        require(tx.time >= unlockTime);
    }
}
      • The key. Opening a jar creates one NFT of a fresh category and sends it to the wallet. Its commitment is the unlock time.
      • The jar's address follows from the key alone: P2SH32( SavingsJar(key.category, key.commitment) ). That is rule 3.
      • One contract for every wallet. An ordinary wallet holds the key NFT at a P2PKH address and the application builds the transaction. Grandma's Wallet holds it at a recoverable address and builds the transaction itself. The jar cannot tell the difference.
      The jar's transactions

        The jar trusts the category. Only the transaction that opens the jar can create tokens of it, and the wallet builds that transaction from the template with exactly one NFT. A wallet that made two keys for one jar would only have two keys to its own jar.

        Work this needs in the wallet: actions that create a token. The current build refuses them. Creating a category also needs a wallet coin that is output 0 of its transaction, so the wallet may first have to make one by paying itself.

        ParyonUSD open

        ParyonUSD lends its dollar token, PUSD, against BCH collateral. Each loan is managed by whoever holds its loan key NFT. That is rule 1 already, on chain, in contracts we would not change. The plan is to write our own front end and XO template for it and to show a real loan surviving a recovery on Paryon's chipnet deployment.

        A loan, from the wallet's side
          Rule 1 · AuthorityMet

          The loan key is a bearer NFT. The borrowing contract checks its category and amount and not where it is sent.

          Rule 2 · Wallet's partsContracts yes, front end no

          The five contracts read put no condition on the wallet's script. The official front end accepts P2PKH wallets only.

          Rule 3 · Finding the loanTo be written

          The sidecar coin carries the loan key's category, so the loan can be found from the key. The template that says so is ours to write.

          What was checked, and what was not

          Checked

          • Paryon's test deployment chipnet-fast-periods-6 answered on 17 November 2026 with 4 active loans and an oracle price of $274.4.
          • Sources of Borrowing, LoanKeyFactory, LoanKeyOriginEnforcer, LoanKeyOriginProof and manage, from the npm package @paryonusd/contracts 1.1.0. The layouts in the diagrams are taken from them.
          • The minimum loan is 100 PUSD at 110% collateral, about 0.4 BCH at that price, plus a 0.25% fee.

          Not checked

          • Nothing has been sent. No loan was opened from a script address.
          • Whether an XO template can express a transaction with four Paryon contract inputs and seven fixed outputs, with the wallet supplying only its own parts. This is the main risk, and it is the claim the demo is meant to prove.
          • The other 21 contracts (interest, redemption, liquidation, staking) were not read for this purpose.
          • Paryon's transaction-building library is not public. We write ours from the contracts.

          Before any front end: open, manage and close one loan on chipnet from a recoverable address with a plain script. That settles whether the contracts accept this wallet. It needs about 0.5 test BCH. Paryon's contracts repository states no licence, so we would depend on the npm package without copying it, and telling the Paryon team would be sensible.

          Privacy later

          Version 1 is no more private than a wallet with one address. The design keeps the door open for a version 2 that is, without changing the controller, the recovery flow or the application rules.

          Version 1 · for the hackathon
          • One address per owner key.
          • The identity is written in the address script, visible when a coin is spent.
          • The controller's state is readable: owner key hash, recoverer key hash, delay.
          • A new device needs only the identity.
          Version 2 · later
          • A fresh key per address, from one seed.
          • Each address carries hash(identity ‖ address secret). The identity shows only in a sweep.
          • The controller's state is a hash. It moves only at recovery.
          • A new device needs the identity and a viewing secret that the recoverer keeps.
          contract RecoverableAddressV2(bytes32 tag, bytes20 keyHash) {
    function spend(pubkey pk, sig s) { /* as before */ }
    function sweep(bytes32 identity, bytes32 addressSecret) {
        require(hash256(identity + addressSecret) == tag);
        ownerApproves(identity);
    }
}

          What keeps version 2 possible

          • Applications never see the identity or the controller. The rules speak only of tokens and of addresses the wallet supplies, so a change of address scheme is invisible to them.
          • The address script has a version. A wallet can hold coins at addresses of both versions and sweep both.
          • The controller is off the everyday path. In version 1 it already appears only at setup, recovery, sweeps and vault spending.

          What version 2 would still show: a sweep ties the swept addresses to one identity. Several controllers, each covering part of the addresses, limit that. Hiding it fully needs a zero-knowledge proof checked in script, which Bitcoin Cash cannot practically do today as far as we know.

          Order of work

          1. The recoverable address. Contract and tests: both paths, the sweep, and every refusal shown on this page.
          2. Wallet on the key path. Receive at the recoverable address, pay with the key, keep the vault.
          3. Sweep on a new device. Addresses from the controller's history; coins and tokens moved after completion.
          4. Token-creating actions in the wallet, including the output-0 coin a new category needs.
          5. The new Savings Jar, its template with the recovery declaration, checked with Grandma's Wallet and with an ordinary wallet.
          6. xo_v1 version 3.
          7. ParyonUSD. First a loan from a script address by plain script. Then the template and the front end. Then the recovery of a live loan.
          8. Two short specifications for XO: the recoverable address, and the three application rules as a template profile.

          Costs and open points

          Costs of the design

          • An earlier key works until the sweep. Someone who later finds the lost phone can take a coin that was not swept. The new device should sweep as soon as recovery completes. During the waiting period itself the old key works in the current build as well.
          • Payments to an earlier address. A coin sent to an old address after recovery can be moved by the new owner through the controller, and also by the earlier key. People who pay the wallet need the new address, or the vault address, which does not change.
          • The address changes at recovery. So does every "send it back where it came from" in an application: it refers to the new address only after the sweep.
          • The sweep links addresses. In version 1 they are public anyway.
          • A request is not cancelled by ordinary use. The owner's device has to notice it. The monitor runs only while the wallet page is open, as today.

          Open points

          • Template fit for large application transactions. Untested for ParyonUSD, see above.
          • The template extension. Whether "the wallet's own address" and the recovery declaration belong in the XO schema or in a companion document is for XO to say.
          • Application state that is not on chain. Accounts opened by signing a message with a key, or state kept on a server, are outside these rules.
          • Positions that change without the wallet. A liquidated or redeemed loan leaves the wallet holding a key to nothing. The template's way of finding the position has to cope with "not found".
          • Size and fee of a script-address spend compared with P2PKH: not measured.
          • None of the contracts is audited.
