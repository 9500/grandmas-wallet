Grandma's Wallet

A Bitcoin Cash wallet whose keys can be replaced by a trusted recoverer after a public waiting period. Every coin has its own address and key, as in an ordinary HD wallet. A single controller on chain can release any of them to a new owner. Applications give authority to a token in the wallet, so recovering an application position is the same as moving a coin.

The design

Every ordinary address of the wallet can be spent in two ways. Its own key spends it directly, like any single-key address. The wallet's controller can also release it, and the controller obeys whoever owns the wallet's identity today. Recovery changes the owner of the identity. The new owner then moves every coin and token to addresses of its own keys.

Two ways into every coin

The parts

Wallet

Controller. One coin holding the identity NFT. Its state names the owner's controller key, the recoverer's key and the waiting period. It moves only for recovery, sweeps, the vault and changes of settings.

Wallet

Recoverable addresses. One per coin, each with its own key for every day and a hidden link to the identity for recovery. A second kind, the vault address, has no key and never changes.

Recovery

Recoverer and viewing key. The recoverer can replace the owner after the waiting period. It also keeps the viewing key, which lets a new device find every address. Neither lets it spend.

Applications

Three rules and a connection. Authority is a token. The wallet's inputs and outputs are the wallet's business. The template says what a token means. The wallet builds each transaction from the application's XO template.

Identity and controller

The wallet's identity is the token category of one NFT. The coin that holds this NFT is the controller. The NFT's commitment is the controller's state, 69 bytes. The controller's script accepts five actions. Four of them send the NFT back to itself with the next state. The fifth closes the wallet and destroys the NFT.

ActionSigned byWhat it doesUsed for
ownerAuthorizeOwner's controller keyContinues the controller unchanged as Active. Cancels a pending request.Sweeps, spending from the vault, cancelling a request
requestRecoveryRecoverer's keyMarks the state Pending and names the proposed new owner key. The waiting period starts.The first step of recovery
finalizeRecoveryRecoverer's keyOnly after the waiting period. Installs exactly the proposed key and raises the epoch by one.The second step of recovery
ownerUpdateOwner's controller keyReplaces the owner key, the recoverer or the waiting period.Moving to a new seed without the recoverer; changing the recoverer or the waiting period
ownerCloseOwner's controller keyEnds the identity. The transaction has one output without a token, so the NFT is destroyed and the controller's 1,000 satoshis go to that output.Emptying a wallet for good. Not offered in the wallet's ordinary interface.

In every action the signature must cover every input and output. In the four that continue the controller, it is input 0 and output 0 of its transaction, and the NFT and the coin's value continue.

Closing cannot be undone. A vault address works only while the identity's NFT exists, so after closing nobody can spend from one, and a coin that arrives there later is lost. There is no recovery afterwards. The action is part of every controller so that a wallet can be emptied to the last satoshi; the test runs end this way. See Fees and emptying.

The controller's script does not check its own first state. Before trusting an identity, a wallet checks the transaction that created it (one NFT of the category, no way to make another, a valid first state, locked by the controller script) and follows every step of the controller from there to today.

Two properties carry the scheme

  • The waiting period is enforced by the network. It is a relative time lock on the controller's own coin. Nobody can shorten it.
  • The recoverer's key never spends a coin. A coin released through the controller requires the controller to continue unchanged, with the same owner and no request pending. A request leaves a claim pending and a completion changes the owner, so neither can carry coins with it. This check is one shared function, ownerApproves(identity), used by every address script. A recoverer who installs a key of its own after a wait that nobody cancelled is then the owner; that is the trust placed in it.
function ownerApproves(bytes32 identity) {
    // Input 0 is this identity's controller.
    require(tx.inputs[0].tokenCategory == identity + 0x01);
    bytes state = tx.inputs[0].nftCommitment;
    require(state.length == 69);
    require(state.split(1)[0] == 0x01);
    // It continues as Active with the same owner, epoch, recoverer and delay.
    require(tx.outputs[0].tokenCategory == identity + 0x01);
    require(tx.outputs[0].nftCommitment == 0x0100 + state.slice(2, 49) + bytes20(0));
}

Only an owner-signed step produces that successor: ownerAuthorize, or an ownerUpdate that changes nothing. The owner's signature on the controller, which covers the whole transaction, is therefore what approves the release. The simulator under A wallet's life shows the state byte by byte.

Keys and addresses

The wallet works like an HD wallet and uses the same building blocks: twelve words (BIP39) and a tree of keys computed from them (BIP32). One seed on the phone gives a key for every address, and every coin can sit at its own address. What is added is a second, hidden way into each address, and a viewing key that lets someone other than the phone find the addresses again.

Seedon the phone only
Twelve words, made on the phone. Every key below is computed from them, and nothing random is added later. The user is not asked to write them down. Losing the phone loses the seed.
Controller keyfrom the seed
One key on a branch of its own. Its hash is the owner entry in the controller. It is used for nothing else and appears in no address.
Address keysfrom the seed
Two branches, one for each kind of address, whose children are the address keys, counted from 0. The kinds are: given out, for addresses the user hands to people who pay them, and change, for change and for coins and tokens that an application's transaction sends to the wallet.
Blinding seedfrom the seed
32 bytes on a branch of their own. It gives every address a secret: secret = hash256(blinding seed ‖ kind ‖ number).
Viewing keyon the phone and with the recoverer
The extended public keys of the two address branches, which give every address's public key and no private key, and the blinding seed. Together with the identity they find every coin of the seed. They cannot spend one. Neither value alone gives an ordinary address; the blinding seed with the identity gives the vault addresses, which have no key. Each seed has its own viewing key, and earlier ones are kept.
Identitypublic, on chain
The token category of the controller's NFT. It is not written in any address, and it cannot be worked out from the seed: it exists only once the controller has been created.
ValuePlace in the key tree
Controller keym / P' / C' / 0' / 0
Address key, kind c, number im / P' / Ac' / 0' / i   (c = 0 given out, 1 change)
Blinding seedSHA-256 of the private key at m / P' / A0' / B'
Funding keym / P' / W' / 0' / 0
Recoverer's credential, a separate set of twelve wordsRecovery key m / P' / C' / 0' / 0 and fee key m / P' / W' / 0' / 0 of its own tree

This is the key tree of the XO engine, which signs with no other key: every key of a template is at m / P' / T' / 0' / n. P is XO's purpose number, 2415 on mainnet and 42415 on test networks. T is the template's number, which follows from the template's content: C for the controller template, A0 and A1 for the two address templates, W for XO's standard wallet template. n counts up from 0. B is 1,651,272,046, a number of this scheme (the bytes of "blin"). The templates that hold keys never change, because a changed template would give other keys.

Finding everything again

A device that holds the identity and a viewing key finds that seed's coins in two passes. No list of addresses has to be kept anywhere.

  1. Quick pass. For each kind of address it derives number 0, 1, 2 and so on, looks each up on chain, and stops after a run of unused ones: 20 for addresses given out, 5 for change and for vault addresses. This is how any HD wallet is restored, and it nearly always finds everything.
  2. Full pass. It looks up every number of every range. Each kind has a fixed number of addresses per seed, the same for every wallet, so nothing about the ranges has to be stored. This finds what the quick pass can miss, for example an address given out past a gap after the transaction that had closed the gap was dropped.

For each address it finds, the device also has the secret, which is what the recovery path needs. The wallet is reported as fully found only when the full pass has finished for every seed it has had. A server that does not answer gives "incomplete", never "empty".

After a recovery the new device has a new seed and a new viewing key. It gives the new viewing key to the recoverer before the request is made, so the wallet is never without a recovery path. The same holds when an owner moves to a new seed with the old phone at hand: the recoverer confirms that it holds the new viewing key, and only then does the owner key change. Earlier viewing keys are kept: they find payments that still arrive at earlier addresses.

The first coins

An address needs the identity, and the identity is the identifier of a transaction, so the wallet's very first coins cannot arrive at a recoverable address.

  1. Fund. The user sends coins to the wallet's funding address, an ordinary single-key address of the funding key.
  2. Prepare. The wallet pays itself, so that it has a coin that is output 0 of its transaction. That transaction's identifier is the identity.
  3. Create and move. A transaction spends that coin and creates the controller. The rest goes to recoverable addresses, and must hold at least what a cancellation costs. The user may also give the recoverer an allowance for its fees.

The funding address is not recoverable. It is shown only until the wallet exists. The first coins can be traced to the creation of the identity; coins received later at fresh addresses have no such link. If the phone stops part-way, it continues from the transactions that exist and does not start a second identity.

Nothing waits for a block. Each step goes on as soon as the network has the transaction before it. The wallet gives out addresses, the recoverer is enrolled and recovery shows as on while the creation is still on its way into a block. This is safe because every address has two ways in: its own key, which does not involve the identity, and the controller. If the transaction that defines the identity were replaced (only whoever can spend its inputs can do that) or a block that held it were undone, the coins already paid to the wallet's addresses would still be spent by their keys. Only their recoverability would be gone until they are moved.

So the wallet watches the creation until a block holds it. If it disappears, the wallet says so, stops giving out addresses of the identity that no longer exists, keeps watching the ones it gave out and counts what is there as not recoverable, makes a new identity from the coins it has, moves the coins over with ordinary key payments, and asks for the recoverer to be set up again: the old kit names an identity that does not exist.

How an address is made

The wallet makes a new address whenever one is needed. Making one writes nothing on chain and does not involve the controller.

Every address is built in the same steps. Choose a kind and a number to follow them for one example wallet.

number 0

  • The phone can do every step. A holder of the viewing key can do all but the private key: it gets each public key from the extended public key.
  • Nobody can go backwards from an address. The address is a hash of the script. The tag inside the script is a hash of the identity and a secret that only the viewing key gives.
  • Two addresses of one wallet share nothing visible. Each has its own key and its own secret, so each has its own tag.
  • The payer sees an ordinary script address. Nothing shows that it is recoverable or which wallet it belongs to. Spending it by key shows the kind of address, and still not the wallet.
  • The wallet stays inside a window and a range. It shows no address more than 20 numbers past the last used one of its kind (5 for change and for vault addresses), and none past the fixed range of its kind. When the window is full it offers an address it has already given out, and says so.
  • An address made for something that did not happen gets its number used again only if it was never shown and nothing was signed. Otherwise it stays taken and stays watched.

The recoverable address

A script address (P2SH32) with two ways to spend.

contract RecoverableAddress(bytes32 tag, bytes20 keyHash) {
    // Everyday path: the key this address was made for.
    function spend(pubkey pk, sig s) {
        require(hash160(pk) == keyHash);
        require(checkSig(s, pk));
    }
    // Recovery path: whoever owns the identity today, through the controller.
    function sweep(bytes32 identity, bytes32 addressSecret) {
        ownerApproves(identity);
        require(hash256(identity + addressSecret) == tag);
    }
}

contract VaultAddress(bytes32 tag) {
    // No key. Only the identity's current owner, through the controller.
    function spend(bytes32 identity, bytes32 addressSecret) {
        ownerApproves(identity);
        require(hash256(identity + addressSecret) == tag);
    }
}

Compiled, the rules are 96 bytes for the recoverable address and 75 for the vault address, before the tag and the key hash are added. Measured in a trial, an input spent by its key is 296 bytes, a swept input 260 and a vault input 217, against 141 for an ordinary single-key input. The contracts and their tests are the first stage of the plan.

Recoverable address

The wallet's ordinary address, a fresh one for each coin, token and change output. Used for everything the wallet does with applications. After a recovery its contents are swept to addresses of the new seed.

Vault address

For an address that must outlive a key change: one published to be paid at any time, or a payout address agreed long before the payout arrives. It is meant to be used more than once. Spending from it needs the controller at input 0, so a coin is moved from the vault to an ordinary address before an application can use it.

    A wallet's life

    Press the actions in any order. The strip shows the controller's 69 bytes; press a field to read what it is for. The cards show where the coins and tokens sit. Each one is at its own address; the cards group them by the seed their addresses were made from.

    Controller and addresses

      Things to try: complete a recovery and use the loan before sweeping. Complete a recovery and let the earlier seed act before the sweep. Request a recovery, then pay someone, and see that the request stays pending.

      Fees and emptying

      The wallet pays the lowest fee that nodes relay, and works it out from the transaction itself.

      • The rate is one satoshi per byte, which is what nodes require. It is a setting, and the wallet does not raise it by itself.
      • The fee is exact. It is the size of the signed transaction times the rate. The size is known before signing, because signatures, keys and scripts have fixed lengths. The wallet measures the transaction; it does not add up estimates.
      • The smallest output depends on the output. Nodes relay nothing below 546 satoshis at a single-key address, 576 at an address of this wallet, 888 for the controller, and more for an output with a token. The wallet computes this for every output it creates.
      • Change is what can be saved. Every coin costs its bytes once, whenever it is spent. A change output costs bytes now and again when it is spent, so the wallet prefers a choice of coins that needs none.
      • Nothing goes to the fee unseen. If what is left is too small to return as change, the wallet compares leaving it to the fee with adding a coin, takes the cheaper, and shows the amount.
      • A check before sending. The signed transaction must have the size that was worked out, the required fee and no output below its smallest value. There is no limit on the fee in satoshis, which would stand in the way of a transaction with many inputs.

      Where each fee comes from

      TransactionWho paysFrom where

      The controller's 1,000 satoshis are not a fee fund. They are what the output needs to exist, and the script does not let an action spend them, except closing.

      Sending everything

      • What goes: every coin without a token, to one address. There is no change, and the amount is the total less the exact fee.
      • Coins that only the controller can move, at vault addresses or at an earlier seed's addresses, go in the same transaction with the controller.
      • Satoshis under a token stay with the token. They leave when the token is sent, or when the user destroys the token on purpose.
      • It cannot be done only when the total less the fee is below the smallest output. A single coin of 546 satoshis leaves 361, which cannot be sent. The wallet then shows the total, the fee and the smallest output.
      • What is left: the controller, coins with tokens, and whatever the recoverer holds. The wallet stays usable and recoverable. Until it holds Bitcoin Cash again it cannot pay for a cancellation.

      Closing

      Sending everything with ownerClose in the last transaction also takes the controller's value and ends the identity. Measured at one satoshi per byte:

      MeasuredResult
      Closing with no other coin1,000 − 681 = 319 satoshis, below the smallest output: it cannot be sent
      Closing together with other coinsAdds 1,000 satoshis and 637 bytes: 363 satoshis more arrive
      Every other controller transaction45 bytes larger, because the script is longer

      Closing is therefore the last step of emptying a wallet, never a step of its own. A sweep or a vault spend cannot be part of it; what only the controller can move is moved first. The wallet's ordinary interface does not offer it. A tool does, and it refuses while a vault coin or a token is held or before the full search has finished. Whoever holds the owner's key can also build the transaction without this software. The recoverer cannot close.

      Recovery flow

      1. 0

        Setup, while all is well

        Owner and recoverer

        The wallet creates its controller, naming the recoverer's key and the waiting period. It sends the recoverer an enrollment message with the recovery kit, signed by the owner and sealed so that only the recoverer can open it. The recoverer checks it against the chain, saves the kit and leaves a signed receipt. Only then does the wallet say that recovery is on.

      2. 1

        A new device asks

        New device and recoverer

        The new device makes a new seed. It gives the recoverer the hash of its controller key, its own viewing key signed with that key, the access to a new backup, and a key for the answer. It does not need to know the wallet's identity yet. The recoverer satisfies itself that the person is the wallet's user; how it does so is its own process, and the design depends on it.

      3. 2

        Request

        Recoverer

        The recoverer signs requestRecovery naming that key. The controller is now Pending, on chain. The owner's wallet sees the request and warns at once; the waiting period counts from the block that holds it.

      4. 3

        Wait, and the owner's chance to refuse

        Owner, if the phone is not lost

        The wallet watches its controller on several servers. If a request appears that the owner did not ask for, the owner cancels it with one signature of the controller key. Ordinary payments do not touch the controller, so they do not cancel a request. The cancel is a transaction of its own, by hand or automatic, and its fee of about 1,100 satoshis comes from the wallet's coins. A wallet that holds only tokens says on the warning that it needs a little Bitcoin Cash to refuse, and where to receive it.

      5. 4

        Complete and hand over

        Recoverer

        After the waiting period the recoverer signs finalizeRecovery. The proposed key becomes the owner and the epoch goes up. No coin has moved. As soon as the network shows the completion, the recoverer gives the new device the identity, the viewing key of every earlier seed and the access to earlier backups, sealed to the device, and the new device sweeps and gives out addresses.

      6. 5

        Sweep

        New device

        With the identity and the earlier viewing keys the new device finds every address in use: a quick search first, then a full search of every range. It moves what is there to addresses of its own seed, in transactions that carry the controller, signed with ownerAuthorize. Each swept input shows the identity and its address secret. Coins, fungible tokens and NFTs move the same way. The fee comes out of the swept coins. A large wallet is swept in several transactions, the most valuable first. A token the wallet does not understand counts as possibly valuable.

      7. 6

        Understand what the tokens are

        New device, with the applications' templates

        A swept NFT is already under the new owner's control. To show it as "a jar with 0.3 BCH that opens in March" the wallet needs the application's template, from its backup or from the application when the user connects again. Recovery does not wait for this.

      8. 7

        Keep watching

        New device

        The new device watches the controller, and it keeps watching the earlier addresses for payments that still arrive there. Its coins pay for refusing a request, as on any device. See A payment to an old address.

      The recovery kit and the recoverer's key

      • The kit contains the identity, the recoverer's credential for this wallet, the viewing key of every seed, where the sealed backups are kept and how to read them, and the settings as the owner saw them, for the recoverer to compare with the chain. The first kit arrives in one link or one QR code. The recoverer keeps the kit and adds to it whenever the wallet gets a new seed.
      • The recoverer's key is one per wallet, not one per coin. Only its hash is on chain, in the controller. No address contains it, and the recoverer never signs for a coin of the wallet. It signs two kinds of transaction: the request and the completion.
      • The recoverer uses a different key for every wallet, so two wallets with the same recoverer show nothing in common. By default the owner's phone makes this key as a separate set of twelve words, puts its hash into the controller, seals the words into the kit and does not keep them. The same words give a separate fee key.
      • The recoverer pays its own fees, about 2,000 satoshis for a request and a completion, from an ordinary address of the fee key. Its software shows that address, what it holds and what is needed, and anyone can send coins there. The owner may give an allowance when the wallet is created; the suggested amount covers four requests and one completion. It is offered, not required, and once given it is the recoverer's own.
      • A receipt decides. The wallet says that recovery is on only when the recoverer's signed receipt matches what it was sent and the controller's state on chain.
      • A new seed with the old phone at hand, and a new recoverer, follow one order: the recoverer first confirms that it holds what it needs, and only then does the owner sign the change. A recoverer that is replaced keeps what it has already seen.

      What the waiting period does and does not protect. It protects against a recoverer who acts without being asked, as long as the owner notices in time. A recoverer who names their own key and is not cancelled gets the wallet. It does not protect against a thief who can use the owner's phone: such a thief can spend at once, as with any wallet.

      If a recovery completes against the owner's will, the owner's keys still spend every coin that has not been swept. A wallet that finds itself owned by a key it does not hold stops giving out addresses, makes sure of what it sees on more than one server, and offers to move its coins out at once, to a wallet with a new identity. That is a race against the new owner's sweep. Coins at vault addresses cannot be saved this way.

      What still waits for a block, and why

      Everything that can go on before a block does. A transaction that disappears later takes with it only what was built on it: the wallet follows the chain at every check, and coins at addresses of a device stay that device's by key. Three things wait, each for a reason that cannot be designed away:

      • The waiting period of a recovery counts from the block that holds the request. It is a time lock that the network enforces, and a transaction that is not in a block has no age yet. The period is the owner's whole protection, so it is measured by the chain and not by a clock anyone could claim. The owner's wallet shows the request and warns as soon as it is seen; only the count starts with the block.
      • A phone stops for good only when a block holds another owner. The moment the network shows another key as the owner, the phone gives out nothing and takes on nothing. A completion that is not in a block can still lose to the owner's cancellation, so until a block holds it the phone only pauses, and carries on by itself if the change disappears.
      • Time locks of applications, such as a savings jar's date or a loan's periods, belong to their contracts, not to the wallet.

      A payment to an old address

      After a recovery, someone may still pay an address the wallet gave out before: an old invoice, an address saved in an exchange's withdrawal list. That coin is not lost. The new owner collects it through the controller, by the same path as the sweep. This is not the vault address; the two are compared below.

      1. The coin lands at the old address. Receiving runs no script, and nothing on chain tells the payer that the wallet has a new owner.
      2. The new device notices it. It holds the earlier viewing key, which the recoverer handed over. From it the device derives the same addresses the old phone used and keeps watching them: every address that was used, and the window past the last one. From time to time it looks up the whole range again.
      3. The new device collects it. One transaction: the controller at input 0, approved by the new owner, and the coin, unlocked by showing the identity and that address's secret. The secret comes from the earlier viewing key. The coin goes to an address of the new seed.
      4. Until then the coin has two masters. The key the address was made for is on the lost phone, and it still opens the address. This matters only if someone can use that phone.

        The controller is readable on purpose

        Anyone can see that a controller exists, and read its state. Its state names no address. Hiding the state behind a hash would gain little: every transaction of the controller has to show the state to the script, so it would become public the first time the controller is used. Two simple measures do more:

        • The recoverer uses a different key for every wallet. Two wallets with the same recoverer then show nothing in common.
        • The owner's controller key is used for nothing else. It never appears in an address.

        What a recovery reveals

        A sweep has the controller as its first input and shows the identity in every swept input. Everything the wallet held at that moment is tied together, in public. Coins received afterwards at new addresses are not, until they are spent together with coins that are. A token whose history is public, such as a loan key, links its position before and after the sweep.

        Limiting this would take several controllers, each covering part of the addresses. Hiding it fully would need a way to prove the link without showing it, which this project has not found for Bitcoin Cash and does not claim. Neither is part of this design. A later version of the wallet's scripts could add either without changing applications, because applications are never sent the identity or the controller and deal only with tokens.

        Rules for applications

        An application that follows these three rules is recoverable by this wallet, and by any other wallet that implements the same scheme, without knowing that recovery exists.

        Rule 1

        Authority is a token

        Whoever may act on a position is whoever spends its ownership NFT in the same transaction. Payouts go to an address the wallet supplied.

        No user key or key hash inside an application contract. A key cannot be replaced; a token can be moved.

        Rule 2

        The wallet's parts are the wallet's business

        The application does not assume the wallet's inputs are P2PKH or have a fixed size. Tokens and change go to an address the wallet names.

        "Back to the address it came from" is acceptable: after a sweep that is a new address.

        Rule 3

        The token leads to the position

        From the NFT (its category and commitment), the template and the chain, a wallet can find the position, work out what its actions need, and list the actions it offers.

        No application server, no private note and no secret that existed only on the lost phone is needed. What the application itself goes on needing, such as a price oracle, is named in the template.

        Why these are enough

        • Recovery never touches an application contract. The sweep moves the NFT from one wallet address to another. The position stays where it is.
        • The application's transaction layout is its own. The controller is not in application transactions, so an application may fix its input and output positions as it likes.
        • A wallet can recover what it does not understand. An NFT of an unknown application is swept like any coin. Its meaning can be learned later.
        • Part of this can be checked by a program. Whether a template leaves the wallet's outputs to the wallet, and whether its declaration leads to a position on chain, can be checked mechanically. Whether a contract gives authority to the token and to nothing else takes reading and testing it. A checker therefore gives one of three answers: verified, a violation found, or not verified.

        What the rules exclude: positions opened by a key written into the contract, positions whose owner is known only to a server, and front ends that insist on building the transaction themselves from the wallet's public keys.

        Template extension

        An XO template describes an application's roles, actions, transactions, inputs, outputs and scripts, and the engine builds every transaction from it. Two things are missing for recovery: a way to say that an output is locked by whatever address the wallet chooses, and a way to say what a token means. The fragments below are sketches. The field names are proposals; they have not been checked against the XO schema or discussed with its authors.

        1. An output the wallet locks

        "outputs": {
  "jarKeyOutput": {
    "name": "Jar key",
    "description": "The token that opens this jar. Keep it in the wallet.",
    "lockingScript": { "wallet": "receive" },        // a fresh address of the wallet's choosing
    "valueSatoshis": 1000,
    "token": { "category": "$(<keyCategory>)",
               "nft": { "capability": "none", "commitment": "$(<unlockTime>)" } }
  }
}

        A template normally names a locking script for every output. Here it leaves the script to the wallet. The same marker on an input says "any coin of the wallet", with no assumption about its script.

        KindThe wallet suppliesNumber taken
        receiveA fresh ordinary address of the "change" kind, for a coin or token created nowThe next one
        changeA fresh ordinary address of the same kind, for what is left overThe next one
        returnThe script of a named input of the same transaction, which must be a coin of the wallet. For contracts that require a token to go back where it came from.None
        lastingA vault address, for an address stored now and paid laterThe next vault number, or one already given out

        The wallet fills each kind itself and never from an address the application supplies. A return is refused when the named input is not the wallet's, or sits at an address of an earlier seed: such a token is swept first.

        XO's validator rejects properties it does not know, so this form needs XO's agreement. Until then the same is done with what exists: the template declares a variable that holds a locking script, and the request says which kind the wallet is to fill it with.

        2. What a token means

        "recovery": {
  "profile": "recoverable-app-v1",
  "authority": {
    "jarKey": {
      "token": "jarKeyOutput",                       // which output creates the token
      "position": {                                  // how to find what it controls
        "lockingScript": "savingsJarLockingScript",
        "variables": { "keyCategory": "token.category",
                       "unlockTime":  "token.commitment" }
      },
      "actions": ["deposit", "withdraw"]             // what its holder can do
    }
  }
}

        A wallet that holds an NFT and trusts this template fills the two variables from the NFT, builds the jar's address, looks it up on chain and offers the listed actions.

        3. A position found through a companion coin

        "recovery": {
  "profile": "recoverable-app-v1",
  "authority": {
    "loanKey": {
      "token": "loanKeyOutput",
      "position": {
        "companion": { "lockingScript": "loanSidecarLockingScript",
                       "tokenCategory": "token.category" },
        "relative": -1                               // the loan is the output before its sidecar
      },
      "actions": ["manage", "close"]
    }
  }
}

        ParyonUSD keeps a small sidecar coin next to each loan, carrying the loan key's category. The wallet finds the unspent sidecar with that category; the loan is the output before it in the same transaction. Category and place alone are not enough where someone could make a look-alike, so the declaration also has to say what makes a sidecar genuine, and the wallet checks it. That part of the declaration is still to be designed. This reading comes from Paryon's borrowing and manage contracts and has not been run.

        4. The wallet's own templates

        The wallet is itself described by XO templates. The engine derives a template's keys from the template's content, so the controller, the addresses given out and the change addresses are three small templates that never change. A fourth, which holds no key and may change, has the wallet's actions, the address of an earlier seed (which can only be swept) and the vault address. One transaction can take inputs and outputs of several templates; that is how a sweep carries the controller and the coins, and how an application's transaction takes the wallet's coins.

        Trials ran this through the unmodified engine on a local node: one script per address with the wallet's tag, a payment by key, a sweep of several coins each with its own secret, and a new seed taking over an identity that another account created.

        Tying a token to a template without a backup. The backup keeps one line per token saying which template made it. If the backup is gone, the wallet can test a token against each template the user trusts: find the position the way that template's declaration says, and check what it finds.

        Talking to applications

        WizardConnect gives an application and a wallet an encrypted channel, started from an address the application shows as text or a QR code. What travels over it depends on what the wallet offers when it connects.

        Who builds the transaction

        The ordinary flow cannot serve this wallet. It hands the application the wallet's public keys, and the application derives P2PKH addresses from them and builds the transaction itself. This wallet's addresses are scripts that cannot be derived from public keys alone. The live front ends of Moria and ParyonUSD, read on 16 November 2026, both refuse any wallet address that is not P2PKH, over WalletConnect as well.

        The xo_v1 extension

        A wallet announces the extension in the WizardConnect session. Nothing in it names an application.

        { "xo_v1": { "version": 1, "network": "chipnet",
    "profiles":  ["recoverable-app-v1"],           // the application rules this wallet relies on
    "bindings":  ["receive", "change", "return", "lasting"] } }   // what the wallet fills in itself

        The announcement lists no templates. A list of what the user trusts would tell each application which others the user deals with. The application names its template in its request.

        MessageDirectionMeaning
        xo_action_requestapplication → walletThe template's identifier and content hash (and the template itself if the wallet lacks it), the action, the role, the variables, which variables the wallet fills and with which kind, and which of the wallet's tokens the action spends
        xo_action_responsewallet → applicationTaken on, or refused with a reason
        xo_invitation_updatewallet → applicationApproved by the user; sent
        xo_action_resultwallet → applicationThe transaction and the tokens the wallet received, or an error
        xo_positions_request / xo_positionsbothWhich tokens of this template does the wallet hold? Answered only for a template the user trusted in a session with this application.

        Rules the wallet follows

        • An unknown template is shown to the user with its name, description and actions, and is trusted only on their word. The template and its declaration are bound by content hash; a later download does not replace them.
        • The wallet states what it knows about a template: verified, a violation found, or not verified. Verified means that the checks the wallet can run have passed, not that the contract was audited. Not verified is the ordinary state of a template met for the first time. A violation is named, with the rule it breaks and what that means for recovery.
        • The user sees two things before approving: the action in the template's words, and the wallet's own figures from the transaction it built. The application cannot influence the second.
        • A request is carried out at most once. It is identified by its id; a repeat gets the stored outcome, and the same id with other content is refused.
        • The application is never sent the identity, a viewing key, or anything about other applications. It learns the addresses that appear in its own transactions. It can study the chain like anyone.
        • A position is a token. The wallet answers a positions request from the NFTs it holds on chain.
        • The wallet signs with the address keys. The controller is not part of an application's transaction.
        • A token that carries authority is spent only in transactions the wallet built itself from a template the user trusts. Whoever gets such a token spent in a transaction of their own shape can use its authority.
        • A standard signing request is refused. The wallet builds every transaction itself, so it answers no request to sign one that an application built.

        This is the part that most needs XO. XO has invitations and a sync client but no protocol between a website and a wallet. A standard would best come from XO, or as a WizardConnect extension that both projects agree on.

        Savings Jar

        The demonstration application. A jar holds savings until a date. Anyone can pay in. After the date, whoever holds the jar's key NFT can empty it. The jar's contract knows nothing about wallets, keys or recovery.

        contract SavingsJar(bytes32 keyCategory, int unlockTime) {
    // Deposits are ordinary payments to the jar's address.
    function withdraw(int keyInput) {
        // Opens for whoever spends the jar's key NFT in this transaction.
        require(tx.inputs[keyInput].tokenCategory == keyCategory);
        require(tx.time >= unlockTime);
    }
}
        • The key. Opening a jar creates one NFT of a fresh category and sends it to the wallet. Its commitment is the unlock time.
        • The jar's address follows from the key alone: P2SH32( SavingsJar(key.category, key.commitment) ). That is rule 3.
        • One contract for every wallet. An ordinary wallet holds the key NFT at a P2PKH address and the application builds the transaction. Grandma's Wallet holds it at a recoverable address and builds the transaction itself. The jar cannot tell the difference.
        • The key is kept. Anyone can pay in again later, and a jar whose key was destroyed could never be emptied. The contract does not require this; the template's withdrawal returns the key, and the wallet checks that output before it signs.
        The jar's transactions

          The jar trusts the category. Only the transaction that opens the jar can create tokens of it, and the wallet builds that transaction from the template with exactly one NFT. A wallet that made two keys for one jar would only have two keys to its own jar.

          What this asks of the wallet: it must carry out template actions that create a token. Creating a category needs a wallet coin that is output 0 of its transaction, so the wallet may first have to make one by paying itself.

          ParyonUSD

          ParyonUSD lends its dollar token, PUSD, against BCH collateral. Each loan is managed by whoever holds its loan key NFT. That is rule 1 already, on chain, in contracts that need no change. The plan is a front end and an XO template of our own for it, and a real loan surviving a recovery on Paryon's chipnet deployment.

          A loan, from the wallet's side
            Rule 1 · AuthorityMet

            The loan key is a bearer NFT. The borrowing contract checks its category and amount and not where it is sent.

            Rule 2 · Wallet's partsContracts yes, front end no

            The five contracts read put no condition on the wallet's script. Managing a loan requires the key to go back to the address it left, which is the return kind. The official front end accepts P2PKH wallets only.

            Rule 3 · Finding the loanTo be written

            The sidecar coin carries the loan key's category, so the loan can be found from the key. The template that says so is ours to write.

            What was checked, and what was not

            Checked

            • Paryon's test deployment chipnet-fast-periods-6 answered on 17 November 2026 with 4 active loans and an oracle price of $274.4.
            • Sources of Borrowing, LoanKeyFactory, LoanKeyOriginEnforcer, LoanKeyOriginProof and manage, from the npm package @paryonusd/contracts 1.1.0. The layouts in the diagrams are taken from them.
            • The minimum loan is 100 PUSD at 110% collateral, about 0.4 BCH at that price, plus a 0.25% fee.

            Not checked

            • Nothing has been sent. No loan was opened from a script address.
            • Whether an XO template can express a transaction with four Paryon contract inputs and seven fixed outputs, with the wallet supplying only its own parts. This is the main risk, and it is the claim the demonstration is meant to prove.
            • The other 21 contracts (interest, redemption, liquidation, staking) were not read for this purpose.
            • Paryon's transaction-building library is not public. Ours is written from the contracts.

            Before any front end: open, manage and close one loan on chipnet from a recoverable address with a plain script. That settles whether the contracts accept this wallet. It needs about 0.5 test BCH. Paryon's contracts repository states no licence, so the npm package is used as a dependency and not copied, and telling the Paryon team would be sensible.

            One consequence for privacy: managing a loan returns the loan key to the address it left, so the key stays at one address for as long as the wallet does not move it. That address is known to anyone who looks at the loan. A sweep moves the key, and the key's public history then links the loan to the recovery.

            Backup and self-recovery

            What a recovery depends on

            InformationNeeded forIf it is lost
            IdentityEverythingThe recoverer cannot act. It is in the kit.
            Viewing key of every seedFinding coins and showing their secretsCoins at that seed's addresses cannot be found or swept by a new owner. This is the one thing that must not be lost; the recoverer's kit holds them all.
            An application's templateShowing what a token means and using its positionThe token is still swept and safe. The template can be had again from the application or from any copy.
            Which template made which tokenConvenienceThe wallet can test a token against the templates the user trusts.
            LabelsConvenienceNames are lost.

            No record per payment or per address is needed, which keeps the backup small. Backup stores hold sealed copies and cannot read them. The recoverer can read them, so a record counts only if it is signed by a key that the controller's history shows as an owner. A signature does not show when a record was made, so for viewing keys the recoverer's receipt decides which record counts, and a record from an earlier seed never overrides the current owner's. After a recovery, or a move to a new seed, the new device starts a new backup, because the earlier phone knows the key of the old one.

            A backup the user keeps

            The design does not need one and supports one.

            • What to keep for the current seed: the twelve words and the wallet's identity (64 characters). A device with both is the same owner. It recomputes every key and address of that seed, finds its coins by searching, and needs no controller transaction and no waiting period. Nothing more is needed, because the search ranges are the same for every wallet.
            • What that leaves out: addresses of earlier seeds. If the wallet has been recovered or moved to a new seed before, payments that still arrive at earlier addresses, and earlier vault addresses, are found only with the earlier viewing keys. A complete backup adds them.
            • It is not a standard wallet backup. The words alone restore nothing in another wallet, and nothing here without the identity.
            • It goes stale at a recovery or a change of owner, because the wallet then has a new seed. It must be made again, and an old backup cannot undo the change.
            • Whoever holds it has the wallet at once. The waiting period guards against the recoverer, not against someone holding the words.

            Being your own recoverer

            The recoverer's role is a key and the kit. Nothing requires a business: a second device of the user's, or a family member's phone, can hold the kit. A wallet has one recoverer at a time, and the owner can replace it.

            Design choices

            ChoiceAlternativeWhy this way
            The controller stays out of everyday transactionsEvery spend passes through the controller, so a key change takes effect at once and nothing has to moveThat alternative puts one coin into every transaction of the wallet. All activity becomes linkable, only one action can be in flight, two such wallets cannot share a transaction, and every application has to make room for the controller at a fixed position.
            Authority is a tokenThe application's contract names the wallet's identity and checks the controller itselfThe application would have to know this scheme and carry its code. A token is something existing applications already use, and it moves with an ordinary transfer.
            The wallet builds the transactionThe application builds it from the wallet's public keys and the wallet signsThe application would have to understand the wallet's scripts. With a template the wallet knows what it is signing and the application needs no knowledge of the wallet.
            One address per coin, identity hidden in a tagOne address for the whole wallet, with the identity in its scriptA single address makes the wallet as traceable as an account number. The tag costs one hash and one secret per address.
            The recoverer keeps the viewing keyThe new device finds addresses from public data aloneAddresses that can be found from public data can be found by everyone. The recoverer is already trusted with the wallet's future.
            Readable controller stateA hashed stateThe state is shown whenever the controller is used. A key per wallet for the recoverer removes the one field that could link wallets.
            A vault address beside the ordinary onesOnly key-bearing addressesSome payments arrive long after the address was given out. A key-bearing address goes stale at recovery; a vault address does not.

            Costs and open points

            Costs of the design

            • An earlier seed works until the sweep. Someone who later finds the lost phone can take a coin that was not swept. The new device sweeps as soon as recovery completes.
            • Payments to an earlier address. A coin sent to an old address after recovery can be moved by the new owner through the controller, and also by the earlier seed. People who pay the wallet need a new address, or a vault address, which does not go stale.
            • The recoverer can read the wallet. The viewing key shows every address and balance. It gives no power to spend.
            • The viewing key of every seed is needed to recover. Without it the new owner cannot find that seed's addresses or show their secrets. The recoverer has to keep each one; sealed copies are in the backup stores.
            • A recovery is public. The sweep ties together everything the wallet held.
            • A request is not cancelled by ordinary use. The owner's device has to notice it and cancel.
            • Refusing needs a little Bitcoin Cash. No coin is kept apart for it. A wallet that holds tokens or positions and next to no Bitcoin Cash cannot refuse a request until about 1,100 satoshis arrive; the warning says so and shows an address.
            • Larger transactions. Spending a script address costs more bytes than P2PKH: 296 for an input spent by its key against 141, as measured.
            • The first coins are traceable. They can be followed to the creation of the identity.
            • Applications have to be reached through a template. Front ends that build transactions from the wallet's public keys cannot serve it.
            • A complete search is a long one. It looks up every address of fixed ranges, for every seed the wallet has had. A seed has a fixed number of fresh addresses; after that the wallet uses addresses again or the owner moves to a new seed.
            • An old identity can outlive its rules. A vault address that was published goes on being paid, so a wallet that moves to new controller rules keeps the old identity in service.
            • Templates that hold keys can never change. A change means other keys: a new seed's worth of addresses, or a new identity.
            • Closing has a price. The action makes every controller transaction 45 bytes larger, and closing turns the identity's vault addresses into addresses nobody can spend from.

            Open points

            • The ranges. The sizes proposed from measurement are 10,000 addresses given out, 10,000 for change and 1,000 vault addresses for each seed, with the full search repeated once a week.
            • Confidence in the chain. The phone takes what is in a block from the servers it is set up with, the user's own node among them. It shows it as information, and waits for it only for the three things under "What still waits for a block". Checking block headers on the phone is later work, and until then the wallet does not call chain state verified.
            • Watching on a phone. A phone that is switched on is not thereby watching the chain. Background operation on phones has to be shown before protection is claimed.
            • Whether closing stays. A released wallet could keep the action in the controller, keep it out of the interface as now, or offer it.
            • Who makes the recoverer's key. The owner's phone by default; the recoverer could make it instead.
            • Template fit for large application transactions. Untested for ParyonUSD, see above.
            • The template extension. Whether "the wallet's own address" and the recovery declaration belong in the XO schema or in a companion document is for XO to say.
            • Application state that is not on chain. Accounts opened by signing a message with a key, or state kept on a server, are outside these rules.
            • Positions that change without the wallet. A liquidated or redeemed loan leaves the wallet holding a key to nothing. The template's way of finding the position has to cope with "not found".
            • The extended public key and a leaked address key. As in any HD wallet, the two together give every key of the chain. The viewing key must stay away from anyone who could also obtain one of the wallet's private keys.
            • None of this is audited.
